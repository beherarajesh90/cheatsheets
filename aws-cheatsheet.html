00

Learning roadmap

Seven stages, in the order interviewers tend to build on. Foundations and compute are shared by both tracks; AI/ML forks off after networking & security, since Bedrock and SageMaker workloads still live inside a VPC and behind IAM.

01

Foundations

Regions, accounts, and IAM. Almost every technical interview opens here because every later answer — "who can call this, from where" — depends on it.

Core

Global infrastructure

  • Region — an independent geographic area (e.g. us-east-1). Resources don't cross regions by default; most services are region-scoped.
  • Availability Zone (AZ) — one or more discrete data centers with independent power/network, low-latency links to other AZs in the region. Design for at least 2 AZs to survive one AZ failure.
  • Edge location / PoP — CloudFront and Route 53 caching/DNS points, far more numerous than regions, used for latency-sensitive delivery.
  • Availability is bought with redundancy across AZs, not by making one instance bigger.

Shared responsibility model

IAM: the mental model

  • Principal (user, role, or service) makes a request → IAM evaluates every attached identity-based and resource-based policy.
  • Default is implicit deny. An explicit "Effect": "Deny" anywhere always wins over any "Allow".
  • Prefer roles over long-lived access keys. EC2 instance profiles, Lambda execution roles, and ECS task roles hand out short-lived credentials via STS automatically.
  • AssumeRole via STS is how cross-account and cross-service access works — a Lambda function doesn't get "AWS credentials," it gets temporary ones scoped to its execution role.

Interview checkpoint

CoreA user has an Allow policy for S3 full access and an explicit Deny on s3:DeleteObject. Can they delete an object?

No. Explicit deny always overrides any allow, regardless of how the allow was granted (identity policy, group policy, or resource policy). Evaluate deny first — it's the one rule that never loses.

CoreWhy prefer IAM roles over access keys for an EC2-hosted service?

Roles issue temporary credentials via STS, rotated automatically, scoped to an instance profile — nothing long-lived to leak in a config file or commit. Access keys are static secrets you must rotate and store yourself; use them only for cases with no AWS-native identity (e.g. a workload outside AWS, mitigated by IAM Roles Anywhere).

JavaYour Spring Boot app on EC2 needs to read from S3. How do you get credentials into the AWS SDK without hardcoding them?

Attach an IAM role to the EC2 instance profile with an s3:GetObject policy scoped to the bucket/prefix. The AWS SDK for Java's default credential provider chain picks up instance metadata credentials automatically (or the container/task role under ECS) — no keys in application.properties.

AI/FDEYou're deploying an agent into a customer's AWS account. What IAM approach minimizes blast radius?

Cross-account role with a tightly scoped trust policy (only your vendor account/role as principal, ideally with an sts:ExternalId condition to prevent the confused-deputy problem), least-privilege permissions limited to the exact resources the agent touches, and no standing keys — everything through AssumeRole with a short session duration.

Interview checkpoint

JavaYour Lambda-hosted Java service has unacceptable cold-start latency. What are your options?

In order of effort: increase memory (which also raises allocated CPU, speeding JVM init); enable SnapStart (restores from a pre-initialized, cached Firecracker snapshot — biggest single win for JVM Lambdas); trim dependencies and avoid heavy DI framework startup; use Provisioned Concurrency to keep warm execution environments; or compile to a native image with GraalVM to cut JVM startup entirely. For steady, latency-sensitive traffic, reconsider whether Fargate is a better fit than Lambda.

CoreWhen would you choose ECS over EKS?

ECS when you want AWS-native simplicity — task definitions, no cluster control plane to reason about, tight IAM-per-task integration, and the team has no existing Kubernetes investment. EKS when you need Kubernetes-specific tooling/portability, multi-cloud consistency, or the org already runs K8s elsewhere and wants one operational model.

CoreHow does Fargate change the security boundary compared to EC2-backed ECS?

With Fargate, AWS manages the underlying host — no shared kernel with other customers' tasks to reason about, no OS patching. You're responsible for the container image, IAM task role, and network placement (subnets/security groups); AWS owns the node.

Interview checkpoint

CoreDynamoDB or RDS for a new service — how do you decide?

DynamoDB when access patterns are known up front, you need predictable low-latency at high scale, and you can design around a partition key (+ optional sort key / GSIs) instead of ad-hoc joins. RDS when you need multi-table joins, ad-hoc queries, strong relational integrity, or the team's existing tooling (JPA/Hibernate) assumes SQL. Many systems use both — RDS for the system of record, DynamoDB for a specific high-throughput path.

JavaHow do you keep RDS credentials out of your Spring config?

Store them in Secrets Manager (with automatic rotation) and fetch at startup via the AWS SDK, or use RDS IAM database authentication so the app assumes a role and gets a short-lived auth token instead of a static password — no secret to rotate or leak at all.

AI/FDEWhere does S3 fit in a RAG pipeline?

It's usually the source of truth for raw documents — the ingestion Lambda reads new/updated objects (often via an S3 event trigger), chunks and embeds them, and writes vectors to the retrieval store. S3 versioning also gives you a natural audit trail for what content the model was allowed to retrieve at a given time.

Interview checkpoint

CoreWhy does a private-subnet EC2 instance still need a NAT gateway to install OS updates?

A private subnet's route table has no route to an Internet Gateway, so instances there have no way to reach the public internet directly. A NAT Gateway in a public subnet has an Elastic IP and a route to the IGW; the private route table sends 0.0.0.0/0 traffic to the NAT, which performs outbound-only address translation — the instance can call out, but nothing can initiate a connection in.

CoreWhat's a VPC endpoint and why use one for S3?

It lets private resources reach an AWS service without traversing the public internet or a NAT gateway — cheaper (no NAT data processing charge) and more secure (traffic stays on the AWS backbone). Gateway endpoints (S3, DynamoDB) attach to route tables; interface endpoints (most other services, including Bedrock) use an ENI with a private IP in your subnet.

AI/FDEA customer requires that no traffic to Bedrock ever traverses the public internet. How do you satisfy that?

Create an interface VPC endpoint for Bedrock (and Bedrock Runtime) in the customer's VPC, with a security group scoping which resources can reach it. Application calls resolve to a private IP inside the VPC; the request stays on AWS's private network end to end. Combine with VPC endpoint policies to restrict which specific models/actions are callable.

Interview checkpoint

CoreSQS vs. SNS vs. EventBridge — one-line rule of thumb?

SQS: one message, one consumer, buffered. SNS: one message, many dumb consumers, immediate fan-out. EventBridge: one event, routed by content/pattern to many targets, with schema registry and third-party SaaS sources built in — reach for it when routing logic itself is non-trivial.

JavaYour SQS consumer occasionally fails to process a message. How do you stop it from being retried forever?

Configure a redrive policy pointing to a Dead-Letter Queue with a maxReceiveCount; after that many failed receives (visibility timeout expiring without deletion), SQS moves the message to the DLQ automatically. Set the consumer's visibility timeout comfortably above your Lambda/worker's typical processing time to avoid duplicate concurrent processing.

AI/FDEWhy put Step Functions in front of a multi-step Bedrock agent pipeline instead of one big Lambda?

Long-running/multi-call LLM workflows (retrieve → augment → generate → validate → maybe retry) benefit from Step Functions' built-in retry/catch per state, visual execution history for debugging a bad run, and freedom from Lambda's 15-minute timeout — each state can call out independently and the orchestration survives across calls.

DevOps & observability

Infrastructure as code, CI/CD, and the telemetry that tells you whether the last deploy actually worked.

CodePipeline

Orchestrates source → build → test → deploy stages across other CodeX tools or GitHub.

CodeBuild

Managed build runner — mvn package, Docker build/push, all defined in buildspec.yml.

CodeDeploy

Blue/green and canary rollout to EC2, ECS, or Lambda with automatic rollback on alarm.

CloudWatch

Metrics, Logs, Alarms, and Dashboards — the default place a Java app's stdout ends up.

Interview checkpoint

CoreBlue/green vs. canary deployment — what's the actual difference?

Blue/green stands up a full parallel environment and cuts traffic over all at once (or on a defined schedule), with instant rollback by cutting back. Canary shifts a small percentage of traffic to the new version first, watches metrics, then ramps up gradually — catches regressions on real traffic before full exposure, at the cost of a longer rollout window.

JavaHow would you structure a CI pipeline for a Spring Boot service deploying to ECS?

CodeBuild stage runs mvn verify (unit + integration tests), builds a Docker image, pushes to ECR; CodePipeline then triggers CodeDeploy with a blue/green ECS deployment, shifting traffic via the ALB's target groups with a CloudWatch alarm configured to auto-rollback on elevated 5xx rate.

AI/ML core: Bedrock & SageMaker

The two services that anchor almost every AI Engineer / FDE interview. Know the boundary: Bedrock is "call a foundation model as an API," SageMaker is "own the full ML lifecycle."

AI / FDE
Amazon BedrockAmazon SageMaker
What it isManaged API access to foundation models (Claude, Nova, Llama, Titan, etc.)Full platform to build, train, tune, and host your own models
You managePrompts, orchestration, guardrails, retrievalData prep, training code, hyperparameters, infra sizing
Typical FDE useRAG / agents on top of a hosted LLM, fast to stand up in a customer VPCFine-tuning a domain model, custom embeddings, batch scoring at scale
Pricing shapeOn-demand per-token, or Provisioned Throughput for guaranteed capacityPay for training compute-hours + hosting instance-hours (or Serverless Inference)

Bedrock building blocks

  • Model access — request access per model per account/region; call via InvokeModel / Converse API, streaming or not.
  • Knowledge Bases — managed RAG: point it at an S3 source, it handles chunking, embedding (via a Titan/Cohere embedding model), and vector storage (in OpenSearch Serverless, Aurora pgvector, Pinecone, or Redis) for you.
  • Agents — model plans and calls tools (Lambda-backed "action groups") in a loop to complete a multi-step task, optionally grounded by a Knowledge Base.
  • Guardrails — configurable content filters (denied topics, PII redaction, word filters, grounding checks) applied to prompts and responses independent of the model itself.
  • Provisioned Throughput — reserved model capacity for predictable latency/cost at volume, vs. on-demand's pay-per-token with noisier latency under load.

SageMaker pipeline

Interview checkpoint

AI/FDEA customer wants a chatbot answering from their internal docs. Bedrock alone, or Bedrock + SageMaker?

Start with Bedrock alone: Knowledge Base for retrieval, a hosted foundation model for generation, Guardrails for safety — no training required, days not weeks to a working prototype. Reach for SageMaker only if you need a custom embedding model tuned to their domain vocabulary, or the foundation models genuinely underperform on their task after prompt/retrieval tuning — that's a much higher bar to justify.

AI/FDEOn-demand vs. Provisioned Throughput for Bedrock — how do you decide for a customer?

On-demand for unpredictable or low/medium volume — you pay per token, no commitment, but latency can vary under shared load. Provisioned Throughput for predictable high-volume production traffic needing consistent latency — you commit to reserved model units, typically with a term discount, which only pays off once utilization is high enough to beat on-demand's per-token cost.

AI/FDEWhat's SageMaker Model Monitor actually watching for, and why does it matter post-deployment?

Statistical drift between the data distribution the model was trained on and the data it's currently scoring — feature drift, and (with ground truth) quality/accuracy drift. It matters because a model's offline accuracy says nothing about tomorrow, once the customer's real-world input distribution shifts; Model Monitor is what turns "we shipped a model" into "we know when to retrain it."

RAG & agent architecture

The single most-asked system-design prompt in AI Engineer/FDE interviews: "design a retrieval-augmented system on AWS." Know the two separate flows — ingestion and query.

AI / FDE

Agents vs. plain RAG

Plain RAG is retrieve-then-generate — one retrieval pass, one generation call. An agent adds a reasoning loop: the model decides which tool to call (retrieval, a database query, an internal API), inspects the result, and decides whether to call another tool or answer — useful when the task needs multiple steps or the retrieval query itself depends on intermediate results.

Interview checkpoint

AI/FDEWalk through what happens when a document is updated — how does the retrieval index stay fresh?

The updated object lands in S3, an S3 event (or Bedrock Knowledge Base's built-in sync) fires the ingestion Lambda, which re-chunks and re-embeds just that document and upserts its vectors — old chunk IDs for that source get deleted first so stale content doesn't linger in results. Bedrock Knowledge Bases handles this sync natively if you're using the managed path instead of hand-rolling it.

AI/FDEHow do you stop the model from hallucinating an answer when retrieval finds nothing relevant?

Score retrieved chunks by similarity and set a relevance threshold — below it, don't pass any context and instruct the model (in the system prompt) to say it doesn't know rather than guess. Bedrock Guardrails' grounding check can also flag ungrounded claims in the output; combine with citations so a low-confidence answer is visibly unsupported rather than silently wrong.

AI/FDEWhy choose OpenSearch Serverless over Aurora pgvector for the vector store?

OpenSearch Serverless when retrieval is the primary workload, you want managed scaling and don't want to run/size a cluster, and you may want hybrid (keyword + vector) search. Aurora pgvector when the team already runs Postgres and wants vectors alongside existing relational data in one engine, at typically lower cost for smaller datasets, trading off some of OpenSearch's purpose-built vector-search scaling.

Forward-deployed engineering patterns

What makes an FDE interview different from a pure AI Engineer one: you're not just building the system, you're shipping it inside someone else's account, someone else's security posture, someone else's compliance obligations.

AI / FDE
  • AWS Organizations + SCPs — the customer's org almost certainly has service control policies restricting what any role, including yours, can do — expect denies that aren't in the IAM policy you were handed, and know to check SCPs, not just identity policy, when access "should work" but doesn't.
  • PrivateLink — the standard way to expose a service (yours, or AWS's) to a VPC without a public endpoint or VPC peering's broader network exposure.
  • Direct Connect vs. Site-to-Site VPN — Direct Connect is a dedicated physical link (higher throughput, consistent latency, costlier, slower to provision); VPN is IPsec over the public internet (fast to stand up, variable latency) — often used as DX's automatic failover path.
  • Data residency — confirm which region(s) the customer requires, and that any managed AI service (Bedrock model, Knowledge Base storage) is provisioned in-region — some foundation models aren't available in every region.
  • The FDE trade-off — you're optimizing for this one customer's constraints while a product team optimizes for the general case; the job is knowing which customizations should become platform features and which should stay a one-off.

Interview checkpoint

AI/FDEA customer's security team asks: "does any of our data ever leave our AWS account?" How do you answer, concretely?

Walk the data path: documents stay in their S3 bucket; embeddings are computed by Bedrock via a VPC interface endpoint (PrivateLink) inside their VPC, so the request never touches the public internet and Bedrock, per AWS's data handling terms, doesn't use it to train models; the vector store and app run in their account behind their own IAM. The only thing that leaves is the model inference call itself, and it stays on AWS's private network.

AI/FDEHow would you scope the IAM role you request from a customer for a first deployment?

List the exact actions and resource ARNs needed — bedrock:InvokeModel on specific model ARNs, s3:GetObject/PutObject scoped to one prefix, not the account's whole S3 estate — and propose it as a time-boxed role for initial setup, separate from the narrower runtime role the deployed app actually uses day to day. Asking for less up front is what gets you unblocked faster with a security team, not slower.

Cost & the Well-Architected Framework

Six pillars interviewers use as a checklist when they ask "how would you design this" — even if they never say the framework's name.

Core

Operational Excellence

Run and monitor systems to deliver value; automate changes, respond to events, refine procedures.

Security

Protect data, systems, and assets — identity, detective controls, infra protection, incident response.

Reliability

Recover from failure, scale horizontally, test recovery procedures — no single AZ as a single point of failure.

Performance Efficiency

Use compute resources efficiently as demand and technology evolve — right service, right size.

Cost Optimization

Avoid unneeded cost — right-sizing, spot/reserved capacity, eliminating idle resources.

Sustainability

Minimize environmental impact — managed/serverless services generally carry a lower footprint than self-managed idle capacity.

Cost levers specific to AI workloads

  • Model selection — a smaller/faster model (e.g. Claude Haiku) for simple classification or extraction tasks is often both cheaper and lower-latency than routing everything through the largest model available.
  • Prompt caching — Bedrock supports caching repeated prompt prefixes (e.g. a long system prompt or retrieved context reused across turns), cutting cost and latency on multi-turn or repeated-context calls.
  • Batch vs. real-time inference — SageMaker Batch Transform / Bedrock batch inference cost meaningfully less than real-time endpoints when latency isn't the constraint.
  • Right-size compute — for SageMaker training, use Spot instances for fault-tolerant jobs (with checkpointing); for endpoints, autoscale down during off-hours instead of sizing for peak permanently.

Interview checkpoint

CoreGive an example of trading a Well-Architected pillar against another.

Multi-AZ RDS doubles database cost (Cost Optimization) to buy automatic failover (Reliability). Whether that trade is right depends entirely on the workload's actual availability requirement — the answer isn't "always pick reliability," it's showing you can name the trade-off explicitly.

AI/FDEA customer's Bedrock bill spiked. What's your triage process?

Break down spend by model and by caller (CloudWatch metrics / usage logs) to find which workload grew; check for an obvious cause — a prompt regression sending far more context tokens than intended, a retry loop double-invoking on transient errors, or a new feature routing to a larger model than necessary. Then decide the fix: cheaper model for that path, prompt caching, or moving to Provisioned Throughput if volume justifies it.

Resilience, scaling & auth

The follow-up questions after "it works" — does it survive an AZ loss, a region loss, a traffic spike, and does the wrong caller get turned away.

CoreJava

Auto Scaling & load balancer health

  • Target tracking — pick a metric (e.g. average CPU 50%) and Auto Scaling adds/removes instances to hold it there; the default, lowest-effort policy.
  • Step scaling — define scaling steps per alarm breach size (e.g. +1 instance at 60% CPU, +3 at 85%) — more control when load spikes non-linearly.
  • Scheduled scaling — pre-scale for known traffic patterns (business hours, a marketing push) instead of reacting after the fact.
  • ALB health checks — periodic HTTP request to a path (e.g. /actuator/health); after N consecutive failures the target is pulled from rotation, and traffic stops routing there before the instance is even terminated.
  • ALB (L7) routes on host/path/header — one load balancer, many backend services. NLB (L4) passes raw TCP/UDP, preserves client source IP, and handles millions of requests per second at lower, more consistent latency — reach for it for non-HTTP protocols or extreme throughput.

  • DMS (Database Migration Service) — homogeneous or heterogeneous DB migration with ongoing change-data-capture replication for near-zero-downtime cutover.
  • Flyway / Liquibase — version-controlled schema migrations run as part of the Java app's own CI/CD, independent of the data-move itself.

Interview checkpoint

CoreTarget tracking vs. step scaling — when would step scaling actually win?

Target tracking assumes a roughly linear relationship between the metric and needed capacity, and reacts smoothly. Step scaling wins when load spikes are sudden and non-linear — e.g. a flash-sale traffic jump — where you want a much larger capacity jump for a big alarm breach than a small one, which target tracking's single formula doesn't express as directly.

CoreWhen does multi-region active-active justify its cost over Multi-AZ?

When the business's RTO/RPO requirement is near-zero and a full region outage (not just an AZ) is a risk the org must survive — global-scale consumer platforms, financial systems with regulatory continuity requirements. Multi-AZ already gives strong availability within a region at far lower cost; jumping to active-active roughly doubles operational complexity (data replication, conflict resolution, region-aware routing), so it needs a concrete requirement behind it, not just "more resilience is always better."

JavaYour Spring Boot API needs per-user rate limits tighter than API Gateway's default throttling. How do you add that?

A custom Lambda authorizer or a filter in the app itself backed by a fast counter — DynamoDB with an atomic UpdateItem increment and a TTL attribute for the rolling window, or ElastiCache Redis with INCR + EXPIRE for lower latency at higher request volume. API Gateway's usage plans handle coarse per-API-key throttling; anything per-user or business-rule-specific needs this extra layer.

LLMOps & evaluation

Building the RAG pipeline is the easy half. Knowing it's good enough to ship, and staying able to prove that six months later, is the part interviewers probe for.

AI / FDE

Prompt engineering, RAG, or fine-tuning?

Evaluating a model or RAG pipeline

  • Offline, golden-dataset eval — a fixed set of representative queries with expected answers/behavior, scored automatically (exact-match, ROUGE for summarization) wherever the task allows a mechanical check.
  • LLM-as-judge — use a strong model to score outputs on rubric dimensions: faithfulness (is the answer supported by retrieved context), answer relevance, context precision/recall — the RAGAS-style metric set, useful where no single correct string exists.
  • Human eval — spot-check for tone, safety, and edge cases automated scoring misses; keep it small and targeted, not a replacement for the automated suite.
  • Online eval — real-traffic A/B tests, thumbs up/down feedback captured in the product, regression-tested against the golden set before every prompt or model change ships.

Observability & safety

  • Bedrock model invocation logging — send prompts and completions to CloudWatch Logs / S3 for audit; essential for "what did the model tell this customer" questions months later.
  • Tracing multi-step agents — X-Ray or a purpose-built LLM trace tool captures each tool call and intermediate reasoning step, not just the final response — critical for debugging why an agent took a wrong path.
  • Prompt injection defense — treat retrieved/external content as untrusted data, never instructions; delimit it clearly in the prompt; instruct the model explicitly to ignore instructions found inside retrieved text; keep agent tool permissions least-privilege so even a successful injection can't take a destructive action; validate/allowlist tool-call arguments before execution.
  • PII handling — Amazon Comprehend detects/redacts PII before ingestion; Macie classifies sensitive data at rest in S3; Bedrock Guardrails filters PII in both input and output at inference time.

Interview checkpoint

AI/FDEWhen do you actually reach for fine-tuning instead of better prompting or RAG?

When the task needs a systematic change to the model's behavior that prompting can't reliably encode — a consistent output format/style at scale, deep domain jargon prompting keeps missing, or latency/cost gains from a smaller fine-tuned model matching a larger base model's quality — and you have enough labeled examples and the operational budget to retrain and re-evaluate. It never solves a stale- or missing-knowledge problem; that's what RAG is for.

AI/FDEHow do you evaluate a RAG system before it ships to a customer?

Build a golden dataset from real or realistic customer questions with known-correct answers, run it through offline eval scoring faithfulness/relevance/retrieval precision, and human-review a sample for tone and safety. Set a numeric bar (e.g. faithfulness score threshold) as a CI gate so a prompt or retrieval change can't regress silently before the next release.

AI/FDEAn agent has a tool that can delete records. How do you stop a prompt injection from triggering it?

Scope the tool's IAM permissions to the narrowest possible action/resource; require a separate confirmation step (human-in-the-loop, or a second model check) before any destructive call executes; and treat all retrieved/tool-output content as untrusted data the model should never follow as instructions — that boundary lives in the system prompt and in what the tool is even capable of doing, not just in hoping the model resists the injected text.

Embedding dimensionality is a direct trade: higher dimensions capture finer semantic distinctions but cost more to store and search. Where the embedding model supports it (e.g. Matryoshka-style training), truncate to the smallest dimension that still clears your recall bar rather than defaulting to the maximum.

Compliance: both Bedrock and SageMaker are HIPAA-eligible services — using them doesn't make a workload compliant by itself; you still need a signed BAA with AWS and correctly configured encryption, logging, and access controls on your side. For GDPR, data residency is controlled by which region you provision in, and "right to erasure" has to be designed in — deleting a source document should cascade to deleting its embeddings from the vector store, not just the S3 object.

Interview checkpoint

AI/FDEYou're hosting 40 small classification models with light, uneven traffic. One endpoint each, or something else?

A multi-model endpoint — one set of instances, models loaded into memory on demand and evicted when idle. Forty dedicated endpoints would mean forty sets of always-on instances mostly sitting idle; a shared endpoint amortizes that cost, at the trade-off of a cold-load latency hit the first time a rarely-used model is invoked.

AI/FDEWhat does shadow deployment actually protect you from that an A/B test doesn't?

In an A/B test, the candidate's response is still shown to some real users — a bad candidate has real, if limited, blast radius. In shadow mode, the candidate sees full production traffic but its output is only logged, never returned — you get real-world signal on how it behaves at full volume with zero user-facing risk, before it earns any share of live traffic.

System design & behavioral prompts

Full worked prompts, the shape both tracks get asked to whiteboard, plus the behavioral questions specific to shipping inside a customer's environment.

CoreJavaAI / FDE

Prompt 1 — design a rate limiter for a public API

Requirements: per-API-key limit (e.g. 100 req/min), reject over-limit calls fast and cheaply, work across many concurrent Lambda/ECS instances (no in-memory-only counter).

Trade-offs to name out loud: Redis gives lower-latency atomic ops but adds a stateful component to operate; DynamoDB is serverless and scales automatically but conditional-write contention needs care at very high per-key request rates. Fixed window counters are simpler than token bucket but allow bursts at window boundaries — worth mentioning even if you implement token bucket.

Prompt 2 — design a high-fan-out notification service

Requirements: send email/SMS/push to millions of users for a single event, tolerate partial provider failures, avoid duplicate sends on retry.

  • API accepts the notification request, validates, and drops it on SNS (fan-out) or directly into per-channel SQS queues.
  • Per-channel Lambda workers pull from their queue and call the channel provider (SES for email, SNS/Pinpoint for SMS/push).
  • An idempotency key (e.g. hash of user+event+channel) checked against a DynamoDB table before sending prevents duplicate delivery if a worker retries after a partial failure.
  • A DLQ per queue catches messages that fail repeatedly, for later inspection instead of blocking the queue or silently dropping them.

Prompt 3 — enterprise RAG for a customer, data must never leave their VPC

This is the FDE version of the RAG design prompt, and the answer is really three figures already in this guide, connected: the retrieval pipeline (Fig. 9) runs entirely inside the customer's VPC using an interface endpoint to Bedrock so no call crosses the public internet (Fig. 6), and your own access to that account is a scoped, time-boxed cross-account role, never a standing credential (Fig. 10). The interview signal here isn't knowing RAG — it's naming, unprompted, that the deployment boundary is the hard part.

Prompt 4 — real-time chat with presence, on API Gateway WebSockets

Requirements: many clients hold a long-lived connection, messages route to specific recipients, presence ("who's online") stays accurate as connections drop.

Presence: derive "online" from a row existing in the connections table, not a separate flag — the $disconnect route (which also fires on ungraceful drops, via a keep-alive ping/timeout) deletes the row, so presence and routing share one source of truth instead of drifting apart.

Prompt 5 — multi-tenant SaaS RAG platform, hard isolation between customers

Requirements: one platform, many customers, one customer must never see another's retrieved content even under a bug — isolation has to be structural, not just a WHERE tenant_id = ? clause trusted to always be present.

  • Strongest isolation: a separate vector index per tenant (own OpenSearch collection, or own Bedrock Knowledge Base) — a missing filter simply has nothing else to return, not a leaked row.
  • Cheaper at scale: one shared index with a mandatory tenant-id metadata filter enforced at the retrieval-service layer (never optional, never client-supplied) — cheaper to run, but a bug in that one enforcement point is now a cross-tenant data leak, so it earns the same scrutiny as an authz check.
  • Either way, pair it with per-tenant IAM scoping on the S3 prefix documents land in, so ingestion itself can't cross-contaminate tenants upstream of the vector store.
  • The interview answer worth stating explicitly: pick isolation strength by the compliance bar (a healthcare or finance customer usually forces per-tenant indices), not by what's cheapest to operate.

Behavioral question bank — FDE-specific

These probe judgment under the specific tension of the role: you represent the product, but you're standing in front of one customer's very real, very immediate problem. Structure answers as Situation → Task → Action → Result, and make the judgment call itself the point of the story, not just the technical fix.

  • "Tell me about a time a customer asked for something the product genuinely shouldn't support." — what you listened for underneath the ask, what you actually said no to, and what you offered instead.
  • "Describe a project where the requirements were ambiguous or kept changing." — how you found ground truth (a workshop, a working prototype shown early) instead of waiting for a spec that wasn't coming.
  • "How do you decide whether a customer-specific fix belongs in your fork, or should go back to the platform team as a feature request?" — the actual decision criteria you use, not just "it depends."
  • "Tell me about a time you had to say no to a customer's security or compliance team." — how you turned a blocked request into a scoped-down version that still shipped.
  • "Describe debugging something in a customer's environment you had limited visibility into." — what you did with restricted logs/access instead of the full toolkit you'd have in your own account.

Behavioral question bank — Java Developer

Less about a customer relationship, more about engineering judgment under real constraints — ownership, trade-offs made under deadline pressure, and how a production incident actually got resolved.

  • "Tell me about a production incident you diagnosed." — what the telemetry actually showed you first (a CloudWatch alarm, an elevated latency metric), and how you narrowed from symptom to root cause rather than guessing.
  • "Describe a time you chose a simpler design over a more 'correct' one." — the specific trade-off (e.g. a single RDS instance over a sharded design) and what made it the right call given the actual scale at the time.

Java/AWS deep cuts

Second-round questions — the ones that come after you've already shown you know the basics, and the interviewer wants to see where your knowledge actually stops.

CoreJava

KMS: envelope encryption

This is why it's called "envelope" encryption — the data key is the envelope around the data, and the CMK never directly touches the (potentially large) payload; KMS's API only ever encrypts/decrypts small key material, which is also why it stays fast at any data size.

Lambda concurrency & throttling

  • Concurrency = number of in-flight invocations at once, not requests per second. Each concurrent invocation gets its own execution environment.
  • Account/region concurrency limit is shared across every function unless you carve out reserved concurrency for one function (a ceiling that also guarantees that much capacity, taken out of the shared pool).
  • Provisioned concurrency pre-initializes N execution environments so those invocations skip cold start entirely — pay for the reserved capacity whether it's invoked or not, unlike on-demand.
  • Past the limit, new invocations get throttled (429 TooManyRequestsException for sync calls); async invocations (S3, SNS) instead retry automatically and then land in a configured DLQ/on-failure destination.

CloudFront: caching & invalidation

  • Cache behavior per path pattern controls TTLs, which headers/cookies/query strings vary the cache key, and which origin serves it — a single distribution can route /api/* to an ALB with no caching and /static/* to S3 with a long TTL.
  • Invalidation forces edge locations to refetch before TTL expiry — costs per path pattern past the free monthly allowance, so versioned asset filenames (a content hash in the path) are the usual way to avoid needing invalidation at all.
  • Origin Shield adds one more regional caching layer in front of the origin to reduce duplicate origin requests across edge locations during a cold cache.

EKS: IRSA / pod identity

A pod doesn't get IAM permissions from the EC2 node's instance role by default (and shouldn't — that would hand every pod on the node the same broad access). IAM Roles for Service Accounts (IRSA) federates a Kubernetes service account to a specific IAM role via the cluster's OIDC provider: the pod gets a projected token, exchanges it with STS for temporary credentials scoped to just that role — one namespace's pods can have narrower AWS access than another's on the very same node. Pod Identity is AWS's newer, simpler successor to IRSA, removing the OIDC trust-policy boilerplate.

ECR & testing against AWS

  • ECR image scanning (via Inspector) flags known CVEs in an image's OS packages and language dependencies on push and on a schedule — wire the pipeline to fail the build on a critical finding rather than discovering it in production.
  • LocalStack emulates AWS services locally for fast integration tests without hitting real infrastructure or cost. Testcontainers (with its LocalStack module, or a real Dockerized Postgres/Redis) gives the same idea for services you'd rather test against the real engine. Reserve actual AWS-account integration tests for a smaller suite that validates IAM permissions and service quirks LocalStack doesn't fully emulate.

DynamoDB single-table design, S3 lifecycle, and a few more

  • Single-table design — model multiple entity types in one DynamoDB table using generic partition/sort key names (PK/SK) and overloaded prefixes (USER#123, ORDER#456) so related items can be fetched in one query instead of joining across tables (which DynamoDB can't do natively). The trade-off: access patterns must be known up front, since the key design is built around specific queries, not general-purpose flexibility.
  • GSI vs. LSI — a Local Secondary Index shares the base table's partition key with a different sort key, must be created at table creation, and shares its throughput/size limits with the base table. A Global Secondary Index has its own partition (and optional sort) key, can be added anytime, and scales independently — GSIs cover the large majority of real-world secondary-access-pattern needs.
  • S3 lifecycle rules transition objects to cheaper storage classes (Standard → IA → Glacier) or expire them by age automatically. Cross-Region Replication copies objects to a bucket in another region for DR or latency. Object Lock enforces WORM (write-once-read-many) retention — required for compliance workloads where even an admin shouldn't be able to delete a record early.
  • Step Functions Standard vs. Express — Standard is durable and exactly-once, priced per state transition, fits long-running workflows (up to a year). Express is priced per execution and duration, built for high-volume, short-duration workloads (up to 5 minutes), at-least-once semantics.
  • API versioning — URI versioning (/v1/orders) is the most visible and cache-friendly; header versioning keeps URLs stable but is harder to test/bookmark. Either way, the harder problem is a deprecation policy, not the mechanism itself.
  • AppSync (GraphQL) vs. REST — GraphQL fits when clients need to fetch varied, nested shapes of data in one round trip (mobile apps with limited bandwidth); REST stays simpler to cache, secure per-endpoint, and reason about for straightforward CRUD.
  • EventBridge Scheduler is the modern replacement for a cron-triggered Lambda — one-time or recurring schedules with built-in retry, timezone support, and a flexible time window, without needing a rule wired to a fixed cron expression.

Interview checkpoint

CoreWhy does envelope encryption use a data key at all — why not just call KMS Encrypt directly on the data?

KMS's direct Encrypt API caps payload size (4KB) and every call is a network round-trip to a shared service — fine for small secrets, unworkable for large objects or high-volume calls. Generating a local data key means the actual data encryption happens in-process at memory speed for any size, and KMS is only ever asked to wrap/unwrap the small key — one KMS call per object instead of one per byte.

JavaYour Lambda function is being throttled during a traffic spike even though your account-level concurrency limit isn't close to being hit. Why?

Another function in the same account/region is likely consuming shared concurrency, or this function has a reserved-concurrency ceiling set lower than the incoming load. Reserved concurrency both guarantees and caps capacity for one function — check its specific limit, not just the account total, before assuming it's a global capacity problem.

JavaDesign a DynamoDB table for an e-commerce order system — users, orders, and order items, with a "get all orders for a user" access pattern.

Single table, PK = USER#{userId}, SK = ORDER#{orderId} for order items, and a user profile item at SK = METADATA under the same PK — one query on the partition key returns the user plus every order in one round trip. If you also need "get an order by ID directly" without knowing the user, add a GSI with PK = ORDER#{orderId}.

AI/FDE deep cuts

Where the interview goes once you've shown you can stand up a basic RAG pipeline — the tuning knobs, the failure modes, and the quantitative reasoning FDE interviews specifically probe for.

AI / FDE

Back-of-envelope RAG cost & latency

A worked example, the kind an interviewer wants to see you reason through out loud: a customer support RAG system, 5 retrieved chunks of 500 tokens each, a 300-token system prompt, a 50-token user question, a 400-token answer, running Claude Sonnet-class pricing.

ComponentTokensNote
System prompt + instructions~300Fixed per call — a candidate for prompt caching
Retrieved context (5 × 500)~2,500Scales linearly with top-k — the biggest lever on cost
User question~50Variable, usually small
Model output~400Output tokens typically priced several times higher than input

Input ≈ 2,850 tokens, output ≈ 400 tokens per call. At volume, the two levers that actually move the bill are top-k (retrieved chunk count — cut from 5 to 3 chunks if recall holds, and you've cut ~30% of input cost) and prompt caching on the fixed system-prompt prefix if the same instructions repeat across thousands of calls. Latency follows a similar shape: retrieval (vector search, tens of ms) is nearly free next to generation time, which scales with output length — a system prompt asking for a shorter, more structured answer is a latency lever as much as a UX one.

Bedrock tool use & multi-agent collaboration

  • Tool-use / function-calling schema — define each tool as a name, a description the model uses to decide when to call it, and a JSON Schema for its parameters. The model returns a structured tool-call request (not free text) which your code executes and feeds back as a tool result — description quality matters as much as the schema itself, since the model picks tools by reading it.
  • Bedrock multi-agent collaboration — a supervisor agent decomposes a task and delegates sub-tasks to specialized collaborator agents (each with their own tools/knowledge base), then synthesizes their results — reach for it when one agent's tool set and system prompt would otherwise grow unmanageably broad across unrelated domains.
  • Session/conversation memory — an agent's "memory" across turns is usually just the running message history replayed each call (Bedrock Agents session state, or your own DynamoDB-backed session table keyed by conversation id), not persistent model state — long conversations need explicit summarization/truncation once history approaches the context window.

Retrieval quality: chunking, hybrid search, reranking

  • Chunk size/overlap — smaller chunks (100-300 tokens) give more precise retrieval but lose surrounding context; larger chunks (500-1000) preserve context but dilute relevance scoring. A 10-20% overlap between adjacent chunks prevents a fact from being cut exactly at a chunk boundary. Semantic chunking (splitting on topic shifts rather than a fixed token count) tends to beat fixed-size chunking on unstructured prose.
  • Multi-tenant isolation and streaming responses are covered in §14's Prompt 5 and below.

Model selection & streaming

  • Model tier by task — a fast, cheap model (Haiku-class) for classification, extraction, or routing; a mid-tier model (Sonnet-class) for most production RAG/agent work balancing quality and cost; the largest model (Opus-class) reserved for tasks genuinely needing the deepest reasoning, not as a default. Amazon Nova and Titan trade some general capability for tighter AWS-native pricing/latency on simpler tasks; Llama and other open-weight options via Bedrock matter when a customer needs a specific license or wants to self-host the same weights later.
  • Streaming responses — Bedrock's ConverseStream / InvokeModelWithResponseStream return output as a token stream instead of waiting for the full completion; the app forwards that over Server-Sent Events or a WebSocket to the client so the user sees text appear incrementally — the perceived-latency win is usually bigger than any actual total-time reduction.
  • Cross-region inference profiles route a single model invocation across multiple regions automatically for higher throughput/availability than any one region's quota alone — useful when a customer's volume would otherwise hit per-region rate limits.

Interview checkpoint

AI/FDEA customer asks you to estimate monthly Bedrock cost for 50,000 support tickets/day through your RAG system. How do you approach the estimate out loud?

Break it into input and output tokens per call (retrieved context is usually the largest input component), multiply by daily call volume for daily token totals, apply the model's per-token input/output pricing, then multiply by 30. State the assumptions explicitly (top-k, chunk size, average output length) since the estimate is only as good as those — and note that prompt caching or a smaller model for simple tickets are the two biggest levers if the number comes back too high.

AI/FDEWhy rerank at all, if vector search already returns results sorted by similarity?

Embedding similarity is a cheap, general-purpose proxy for relevance computed independently per document; a cross-encoder reranker scores the query and each candidate document together, capturing interactions between them that a fixed embedding can't — meaningfully more accurate, but too slow to run over an entire index, so it's the last narrowing step after retrieval, not a replacement for it.

AI/FDEWhen would you reach for Bedrock multi-agent collaboration instead of one agent with a big tool list?

When the tool list and system prompt for a single agent would span genuinely unrelated domains (e.g. billing lookups and infrastructure diagnostics) — a supervisor/collaborator split keeps each agent's instructions focused and its tool set small, which measurably improves tool-selection accuracy versus one agent choosing correctly among twenty loosely related tools.
