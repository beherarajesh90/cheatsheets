🚀Introduction to System Design
Foundation for every HLD interview — what it is, what's tested, and how to approach it
What is System Design? FOUNDATION

System design is the process of defining architecture, components, modules, interfaces, and data flows of a system to satisfy specified requirements.

Low-Level Design (LLD)
  • Class diagrams, OOP, design patterns
  • Code-level decisions, API contracts
  • SOLID principles, data structures
High-Level Design (HLD)
  • System architecture, component selection
  • Scalability, availability, reliability
  • Tech stack decisions, data flow

How to Answer a System Design Interview FRAMEWORK
  1. Clarify Requirements (5 min) — Functional vs Non-functional. Ask: scale, users, latency, SLA. Don't assume.
  2. Estimate Scale (3 min) — DAU, QPS, storage, bandwidth. Back-of-envelope calculations.
  3. Define API / Data Model (5 min) — Key APIs, DB schema basics, entities.
  4. High-Level Architecture (10 min) — Draw boxes: clients, LB, services, DBs, cache, CDN. Explain data flow.
  5. Deep Dive (15 min) — Pick 2-3 most critical components. Drill down on trade-offs.
  6. Handle Bottlenecks (5 min) — Identify SPOFs, scaling issues, propose solutions.
  7. Wrap Up — Summarize trade-offs, mention what you'd improve.
💡 Golden Rule
Always clarify before designing. "Can I assume read-heavy workload?" wins points. Interviewers want to see how you think, not just what you know.

⚙️Core Concepts
The fundamental pillars of every system design discussion
Scalability CORE

The ability of a system to handle increased load by adding resources.

Vertical vs Horizontal Scaling

✅ Vertical (Scale Up)

  • Simple, no code changes
  • No distribution complexity
  • ACID-friendly

❌ Limits

  • Hardware ceiling
  • Single point of failure
  • Expensive

✅ Horizontal (Scale Out)

  • Unlimited scaling
  • Fault tolerant
  • Commodity hardware

❌ Limits

  • Distributed complexity
  • Consistency challenges
  • Load balancing needed
💡 Interview Tip
Always prefer horizontal scaling for internet-scale systems. Vertical scaling is a quick win but has a ceiling. Mention both and explain why horizontal wins long-term.

Fraction of time the system is operational. Availability = Uptime / (Uptime + Downtime)

High Availability Patterns
  • Redundancy — Multiple instances, no SPOF
  • Active-Active — All nodes serve traffic simultaneously
  • Active-Passive — Standby takes over on failure (failover)
  • Health Checks — Heartbeats detect failures early
  • Circuit Breakers — Prevent cascade failures
  • Geographic Distribution — Multi-region deployments
⚠️ Series vs Parallel Availability
Components in series: Avail = A₁ × A₂ × A₃ (gets worse). Components in parallel: Avail = 1 - (1-A₁)(1-A₂) (gets better). Always add redundancy in parallel!

CAP Theorem CRITICAL

In a distributed system, you can only guarantee 2 of 3: Consistency, Availability, Partition Tolerance

CAP Theorem — Pick 2 of 3 (but P is always needed)
TypeExamplesBehavior during partition
CP — Consistent + PartitionHBase, MongoDB, ZooKeeper, RedisReturns error/timeout (sacrifices availability)
AP — Available + PartitionCassandra, DynamoDB, CouchDBReturns stale data (sacrifices consistency)
CA — Consistent + AvailableRDBMS (single node), LDAPNot partition tolerant — only for single-node!
💡 Interview Must-Know
In real distributed systems, Partition Tolerance is non-negotiable (networks fail). So the real choice is CP vs AP. Financial systems → CP. Social media → AP.

Consistent Hashing MUST KNOW

Maps keys to nodes on a ring so adding/removing nodes only remaps K/N keys instead of all keys (K=keys, N=nodes).

Consistent Hashing Ring — keys distributed across nodes
  • Virtual Nodes (vnodes) — Each physical node gets multiple positions on ring → better load distribution
  • Adding a node → Only K/N keys remapped (vs. all keys in modulo hashing)
  • Removing a node → Only its keys transfer to the next node clockwise
  • Used by → Cassandra, DynamoDB, Memcached, Chord DHT
💡 When to Mention
Bring this up whenever you're distributing data across multiple nodes — caches, sharded DBs, distributed KV stores. It's the answer to "how do you avoid rehashing everything when a node fails?"
Single Point of Failure (SPOF) ELIMINATE

Any single component whose failure brings down the entire system.

Common SPOFs
  • Single database with no replica
  • Single load balancer
  • Single data center
  • Single DNS server
  • Monolithic server
Solutions
  • Replication (primary-replica)
  • Load balancer clusters (VRRP)
  • Multi-region deployment
  • Redundant DNS (Anycast)
  • Microservices + circuit breakers
Latency vs Throughput FUNDAMENTALS
Latency

Time to complete one request. Measured in ms/µs. Goal: minimize for UX. P50, P95, P99 percentiles matter.

P99 latency = 99% requests finish within X ms
Throughput

Requests/data processed per second. Measured in RPS, QPS, MB/s. Goal: maximize for performance.

Throughput = 1 / Latency (for serial) — but parallel ↑ both
⚠️ Little's Law
L = λW — Average requests in system (L) = Arrival rate (λ) × Average time in system (W). If latency doubles, you need 2x capacity to maintain same throughput.

Proxy vs Reverse Proxy NETWORKING
Forward Proxy

Sits between clients and internet. Client knows about it. Hides client identity from server.

  • Client anonymity / VPN-like
  • Content filtering (corporate)
  • Caching for clients
  • Bypass geo-restrictions
Reverse Proxy

Sits between internet and backend servers. Client doesn't know about backend. Hides server identity.

  • Load balancing
  • SSL termination
  • Caching & compression
  • Security (WAF, rate limiting)
  • Examples: Nginx, HAProxy, Envoy

ACID Transactions MUST KNOW
A = Atomicity · C = Consistency · I = Isolation · D = Durability
A — Atomicity

All operations in a transaction succeed or all fail. No partial updates. "All or nothing."

Example: Transfer $100: debit + credit both succeed or both rollback

C — Consistency

Transaction brings DB from one valid state to another. All defined rules/constraints satisfied.

Example: Account balance can't go negative (if constraint defined)

I — Isolation

Concurrent transactions don't interfere. Intermediate states invisible to other transactions.

READ UNCOMMITTEDDirty reads allowed
READ COMMITTEDNo dirty reads (default PostgreSQL)
REPEATABLE READNo phantom reads
SERIALIZABLEFull isolation (slowest)
D — Durability

Committed transactions survive crashes. Written to disk (WAL — Write Ahead Log).

Achieved via WAL, fsync, battery-backed RAID

Bloom Filters DATA STRUCTURE

Space-efficient probabilistic data structure to test if an element is in a set. No false negatives. May have false positives.

How it Works
  • Bit array of size m, initialized to 0
  • k hash functions per element
  • Add: set k bits to 1
  • Check: if all k bits = 1 → "maybe in set"
  • Check: if any bit = 0 → "definitely NOT in set"
Use Cases
  • DB query optimization — avoid unnecessary disk lookups
  • Chrome Safe Browsing — malicious URL check
  • Cassandra — avoid reading SSTables with no data
  • CDN — check if URL cached
  • Spell checker — word in dictionary?

Split large dataset across multiple DB instances, each holding a subset of data. Each shard is an independent DB.

🔄Distributed Systems Concepts
Consensus, leader election, vector clocks, and handling failures
Heartbeats & Failure Detection MONITORING

Periodic signals sent between nodes to indicate they're alive. Missing heartbeats trigger failure detection.

Heartbeat Patterns
  • Node A sends heartbeat to B every 1s
  • If B misses 3 heartbeats → A considered dead
  • False positives: network partition vs crash
  • Phi Accrual Failure Detector (Cassandra) — adaptive thresholds
Timeout Tuning
  • Too short → false positives (GC pause flagged as dead)
  • Too long → slow failure detection
  • Typical: 3-5 seconds for timeout
  • Used by: Zookeeper, etcd, Consul
Leader Election CONSENSUS

Process of selecting one node as the coordinator/master in a distributed system.

Bully Algorithm
  1. Node notices leader is dead, starts election
  2. Sends Election message to all higher-ID nodes
  3. If no response → becomes leader, broadcasts Victory
  4. Higher ID node responds → takes over election

O(n²) messages. Simple but not partition-safe.

Raft Leader Election
  1. Follower times out → becomes Candidate
  2. Increments term, votes for self, requests votes
  3. Majority votes (n/2 + 1) → becomes Leader
  4. Sends heartbeats to prevent new elections

Safe with partitions. Used by etcd, CockroachDB.

💡 Practical Leader Election
In practice, use ZooKeeper or etcd for leader election rather than implementing yourself. They use proven consensus algorithms and handle split-brain scenarios.

Gossip Protocol EPIDEMIC

Peer-to-peer protocol where each node periodically shares information with random peers. Information spreads like an epidemic.

How it Works
  1. Node A has new information
  2. Randomly selects k peers to share with
  3. Each recipient does the same
  4. Converges in O(log n) rounds
Properties & Uses
  • Self-healing — no central coordinator
  • Fault tolerant — node failures don't stop propagation
  • Scalable — O(log n) convergence
  • Used by Cassandra (membership), Amazon DynamoDB, Bitcoin, Consul
Vector Clocks & Logical Clocks ORDERING

Track causal ordering of events in distributed systems without requiring synchronized clocks.

Lamport Clocks
  • Each node maintains counter L
  • Increment L on each event
  • On send: attach L; on receive: L = max(L_local, L_received) + 1
  • Limitation: can't detect concurrent events
Vector Clocks
  • Each node maintains vector [L₁, L₂, ..., Lₙ]
  • Can detect causality AND concurrency
  • If all Vᵢ ≤ Vⱼ → A happened before B
  • If neither dominates → events are concurrent
  • Used by: DynamoDB, Riak, CRDTs

SAGA Pattern TRANSACTIONS

Manage distributed transactions as a sequence of local transactions. Each step publishes events/messages for the next step. If a step fails, compensating transactions undo previous steps.

Choreography Saga

  • Each service listens to events and acts
  • Simpler, more decoupled
  • Harder to trace/debug

Saga = eventually consistent, no distributed locks, high availability. 2PC = strongly consistent, blocking, lower availability. Saga is preferred for microservices.

  • Need ACID transactions / complex joins? → PostgreSQL / MySQL
  • Need sub-ms reads, caching, pub/sub? → Redis
  • Massive write throughput, time-series, always-on? → Cassandra
  • Flexible JSON schema, document queries? → MongoDB
  • Full-text search, faceted search? → Elasticsearch / OpenSearch
  • Graph relationships (social, recommendations)? → Neo4j / Neptune
  • Massive objects/files (images, videos)? → S3 / Object Storage
  • Analytics / BI queries on historical data? → BigQuery / Redshift / Snowflake
  • Global serverless scale, key-value at any QPS? → DynamoDB / Cosmos DB

12. Unique ID Generator (Snowflake) UTILITY
Twitter Snowflake — 64-bit ID Layout
| 1 bit sign | 41 bits timestamp (ms) | 10 bits machine ID | 12 bits sequence |
  • 41 bits timestamp → ~69 years from epoch
  • 10 bits machine ID → 1024 nodes
  • 12 bits sequence → 4096 IDs/ms/machine → 4M IDs/sec/machine
  • Time-sortable (useful for pagination)
  • No coordination needed (machine ID pre-assigned)
UUID v4128-bit random. No ordering. Simpler but larger.
DB auto-incrementSimpler but single point / hard to shard
