Microservices Foundations

What Microservices Actually Are CORE

An architectural style where an application is built as a suite of small, independently deployable services, each owning its own process, data, and business capability. Services communicate over well-defined APIs.

✅ The 5-Property Core Test

Ask these 5 questions to determine if something is truly a microservice:

#PropertyTest Question
1Independently DeployableCan you deploy this service without deploying any other service?
2Organized Around Business CapabilityDoes this service own a single, complete business function?
3Owns Its DataDoes this service have its own database that no other service queries directly?
4Communicates Over NetworkDoes this service talk to others via well-defined APIs (REST/gRPC/events)?
5Designed for FailureDoes this service handle partial failures from its dependencies gracefully?
🚨
Distributed Monolith Red Flag
If your answer to #1 or #3 is "no", you have a distributed monolith — all the downsides of microservices with none of the benefits.
🎯
Interview Answer
Microservices = independently deployable + single business capability + own data store + communicate via APIs. Key difference from SOA: no shared data, no ESB, uses lightweight protocols.

SOA vs Microservices vs Service-Based

SOA (Service-Oriented Architecture) emerged in the early 2000s: coarse-grained services connected through a centralized Enterprise Service Bus (ESB) that handled routing, transformation, and protocol mediation. The ESB became a bottleneck and a single point of failure. Microservices ditched the ESB in favour of smart endpoints, dumb pipes — each service is autonomous, has its own database, and communicates over lightweight protocols (REST, gRPC, Kafka). Service-Based Architecture is a pragmatic middle ground: coarser services that still share infrastructure (sometimes a shared DB) and are easier to operate than true microservices.

🎯
Why did the industry move from SOA to Microservices?
The ESB became a bottleneck and shared governance problem: teams had to coordinate every change through a central bus team. Microservices give each team full ownership end-to-end. The trade-off: you lose the ESB's centralized mediation and must handle resilience, discovery, and observability yourself.

CAP Theorem HOT

In a distributed system you can only guarantee 2 of 3 properties simultaneously: Consistency, Availability, Partition tolerance. Since network partitions are unavoidable in production, you always choose between CP or AP.

ChoiceDatabasesBehavior on partitionUse case
CPZooKeeper, etcd, MongoDB (strong), SpannerReturns error until partition healsBanking, leader election, coordination
APCassandra, DynamoDB, CouchDB, RiakReturns possibly stale dataShopping carts, social feeds, DNS
🎯
PACELC Extension (more realistic)
PACELC adds: even when the system is running normally (no Partition), you still choose between Latency vs Consistency. E.g. DynamoDB: AP/EL (partition → AP; else → low latency). Spanner: CP/EC (partition → CP; else → strong consistency).
BASE vs ACID HOT
ACID — Relational DB guarantees
  • Atomicity — all or nothing
  • Consistency — rules always enforced
  • Isolation — transactions don't see each other
  • Durability — committed = persisted

→ PostgreSQL, MySQL, Oracle. Sacrifices scalability for correctness.

BASE — NoSQL / distributed guarantees
  • BAsically Available — responds even during failures
  • Soft state — data may change without input
  • Eventually consistent — will converge to consistent state

→ Cassandra, DynamoDB, MongoDB. Sacrifices consistency for availability + scale.

PropertyACIDBASE
ConsistencyStrong (immediate)Eventual
AvailabilityMay blockAlways available
ScaleVertical mostlyHorizontal
TransactionsFull ACIDLimited / saga-based
ExamplesBank transfer, inventory deductionSocial media likes, analytics counters
🎯
Interview framing
In microservices, each service uses ACID within its own DB (local transaction). Cross-service consistency uses the Saga pattern (eventual consistency, BASE). The question to answer is: does the business allow eventual consistency here?

Domain-Driven Design (DDD) Essentials HOT
Bounded Context

Explicit boundary where a domain model applies. Inside: consistent language. Outside: translation.

Ubiquitous Language

Shared language between devs and domain experts. "Order" means the same thing in code and conversation.

Aggregate

Cluster of domain objects treated as a unit. Only one root entity. Changes go through the root.

Domain Event

Something that happened: OrderPlaced, PaymentFailed. Immutable, past tense.

Service Granularity

Granularity determines how much responsibility a single service holds. Too coarse → a mini-monolith; too fine → a nano-service with more network hops than logic. The right size aligns with a bounded context: the service encapsulates one cohesive domain capability and can be understood, deployed, and scaled by a single team.

✅ Fine-grained (good)

  • Independent scaling
  • Isolated deployments
  • Focused teams
  • Easier to understand

❌ Too fine-grained (bad)

  • Chatty communication
  • Distributed transactions
  • Complex orchestration
  • Nano-service anti-pattern

Service calls >3 other services per requestAggregate via BFF or event, don't split further
Team larger than 8 people on one serviceSplit along team boundary (Conway's Law)

Rule of thumb
One microservice per bounded context. A service should be independently deployable and represent a complete business capability. Size: ~10–50k LOC, 1 team (<8 people). Start coarser and extract when you feel the pain — premature decomposition is as harmful as a monolith.

Business Capability vs Subdomain Decomposition

Two complementary lenses for deciding service boundaries. Business Capability asks "what does the business do?" — Ordering, Payments, Inventory. It's a good first cut aligned to org structure. Subdomain decomposition (from DDD) asks "how strategically important is this domain?" and drives where to invest your best engineering.

By Business Capability

Decompose based on what the business does: Ordering, Payments, Inventory. Good starting point. Risk: follows org structure too closely (Conway's Law trap).

By Subdomain (DDD)

Core domain (competitive advantage), supporting domain (generic), generic domain (buy off-the-shelf). Prioritize investment accordingly — build the core, buy the generic.

Subdomain TypeWhat it isStrategyExample
CoreYour competitive edgeBuild in-house, best engineersRecommendation engine, fraud detection
SupportingEnables core, but not differentiatingBuild simply, or outsourceInventory management, order fulfilment
GenericCommodity functionalityBuy/SaaS — don't buildAuth (Auth0), email (SendGrid), payments (Stripe)
🎯
When asked "how do you split a monolith?"
Use both lenses: start with business capabilities for a quick map, then apply DDD subdomains to prioritise — build your core domain first, integrate generic domains via SaaS. Use the Strangler Fig pattern to migrate incrementally, never a big-bang rewrite.

REST in Microservices

REST (Representational State Transfer) is the de-facto standard for synchronous inter-service and client-facing APIs. Key constraints: stateless (each request carries all context), uniform interface (HTTP verbs carry meaning), resource-based URLs (nouns, not verbs). In microservices, REST is best for read-heavy, client-facing, or browser-accessible APIs. Use gRPC for internal high-throughput service-to-service calls.

JavaSpring Boot REST — controller + RFC 7807 error response
@RestController
@RequestMapping("/api/orders")
public class OrderController {

    @PostMapping
    public ResponseEntity<OrderResponse> createOrder(
            @Valid @RequestBody CreateOrderRequest req) {
        Order order = orderService.create(req);
        return ResponseEntity
            .created(URI.create("/api/orders/" + order.getId()))
            .body(OrderMapper.toResponse(order));
    }

    @GetMapping("/{id}")
    public OrderResponse getOrder(@PathVariable UUID id) {
        return orderService.findById(id)
            .map(OrderMapper::toResponse)
            .orElseThrow(() -> new OrderNotFoundException(id));
    }
}

// RFC 7807 Problem Details — standard error body
@ControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(OrderNotFoundException.class)
    public ResponseEntity<ProblemDetail> handleNotFound(OrderNotFoundException ex) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(
            HttpStatus.NOT_FOUND, ex.getMessage());
        pd.setType(URI.create("https://api.example.com/errors/order-not-found"));
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(pd);
    }
}

Message Queues & Event Streaming (Kafka) HOT
JavaKafka Producer (Spring Kafka)
@Service
public class OrderEventPublisher {
    private final KafkaTemplate<String, OrderEvent> kafka;

    public void publish(Order order) {
        OrderEvent event = new OrderEvent(
            order.getId().toString(),
            "ORDER_PLACED",
            Instant.now()
        );
        // Key = orderId ensures ordering per order
        kafka.send("orders.events", order.getId().toString(), event)
             .whenComplete((result, ex) -> {
                 if (ex != null) log.error("Failed to publish", ex);
             });
    }
}

@KafkaListener(topics = "orders.events", groupId = "inventory-group")
public void handle(OrderEvent event, Acknowledgment ack) {
    inventoryService.reserve(event);
    ack.acknowledge(); // manual ack for at-least-once
}

Choreography vs Orchestration HOT
🎭 Choreography

Services react to events. No central coordinator. Each service knows what to do when an event arrives.

✅ Pros

  • Loose coupling
  • High resilience

❌ Cons

  • Hard to trace
  • Accidental cycles
🎻 Orchestration

Central orchestrator (Saga) tells each service what to do and waits for responses.

✅ Pros

  • Clear flow
  • Easy to debug

❌ Cons

  • Single point of control
  • Coupling to orchestrator
🎯
When to use which?
Use choreography for simple event fan-out (order placed → notify, update inventory). Use orchestration for complex multi-step workflows with compensation (payment saga). Tools: Temporal, Conductor, Apache Camel for orchestration.
API Versioning Strategies CORE

Services evolve. Versioning lets you introduce breaking changes without breaking existing consumers. Rule: always version from day 1.

Semantic versioning rules
Breaking change (remove field, change type, rename) → major version bump (/v2/). New optional field → additive, no version bump. Deprecation lifecycle: announce → run parallel (/v1/ + /v2/) → sunset /v1/ after migration. In gRPC: field numbers are the contract — never reuse a field number.

Idempotency & Exactly-Once Semantics HOT

An operation is idempotent if applying it multiple times produces the same result as applying it once. Critical for retry safety in distributed systems.

Idempotency Key pattern

Client generates a unique key (UUID) per logical operation and sends it as header. Server deduplicates using this key.

JavaIdempotent consumer with Redis deduplication
@KafkaListener(topics = "order.placed")
public void handleOrderPlaced(OrderPlacedEvent event) {
    String key = "processed:" + event.getEventId();
    Boolean isNew = redis.opsForValue()
        .setIfAbsent(key, "1", Duration.ofHours(24));

    if (Boolean.FALSE.equals(isNew)) {
        log.warn("Duplicate event {}, skipping", event.getEventId());
        return; // Already processed
    }
    // Process exactly once
    inventoryService.reserve(event.getItems());
}

// Alt: DB-based idempotency table
// INSERT INTO processed_events (event_id) ON CONFLICT DO NOTHING
// → Returns 0 rows affected if duplicate → skip processing
🎯
Kafka delivery semantics
At-most-once: commit before processing (can lose messages). At-least-once: commit after processing (can duplicate → need idempotent consumer). Exactly-once: Kafka transactions (enable.idempotence=true + transactional producer) — expensive, only when truly needed. Best practice: at-least-once + idempotent consumer.
Dead Letter Queue (DLQ) & Poison Pill Handling

A DLQ holds messages that a consumer failed to process after N retries. Prevents poison pills (unprocessable messages) from blocking the main queue indefinitely.

JavaSpring Kafka DLQ configuration
@Bean
public DefaultErrorHandler errorHandler(KafkaTemplate<String, Object> kafkaTemplate) {
    DeadLetterPublishingRecoverer recoverer =
        new DeadLetterPublishingRecoverer(kafkaTemplate,
            (record, ex) -> new TopicPartition(
                record.topic() + ".DLT", record.partition()));

    // 3 retries with exponential backoff before DLQ
    ExponentialBackOffWithMaxRetries backOff =
        new ExponentialBackOffWithMaxRetries(3);
    backOff.setInitialInterval(1000);
    backOff.setMultiplier(2.0);

    return new DefaultErrorHandler(recoverer, backOff);
}

Saga Pattern HOT

Manages distributed transactions via a sequence of local transactions, each publishing an event/message. If a step fails, compensating transactions undo previous steps.

JavaSaga Orchestrator (Choreography via Kafka)
// Step 1: Order Service publishes event
@Transactional
public Order placeOrder(CreateOrderRequest req) {
    Order order = orderRepo.save(new Order(req, OrderStatus.PENDING));
    eventBus.publish(new OrderPlacedEvent(order.getId(), req.getItems()));
    return order;
}

// Step 2: Inventory Service listens and reserves
@KafkaListener(topics = "order.placed")
public void onOrderPlaced(OrderPlacedEvent event) {
    try {
        inventoryRepo.reserve(event.getItems());
        eventBus.publish(new InventoryReservedEvent(event.getOrderId()));
    } catch (InsufficientStockException e) {
        // Compensation: notify failure back
        eventBus.publish(new InventoryReservationFailedEvent(event.getOrderId()));
    }
}

Compensating Transactions — Design Rules

✓ Must Be Idempotent

Compensation may be called multiple times (retry on timeout). Use a dedup ID to detect replays.

✓ Semantic Reversal

Don't delete — create an inverse record. Charge → refund. Reserve → release. Email sent → can't unsend, send cancellation instead.

⚠ Non-Compensable (Pivot)

The step after which you cannot roll back (e.g., payment charged). Design compensations for every step before the pivot; steps after it must complete.

✗ Isolation Problem

Intermediate state is visible to other sagas. Use semantic locks (pending status) or versioned writes (optimistic locking) to prevent dirty reads between concurrent sagas.

⚠️
Saga Gotchas
Compensating transactions don't always roll back perfectly (e.g., email already sent). Make compensations idempotent. Track saga state with a Saga Log. Use Temporal / AWS Step Functions for complex sagas. Every saga step must have a timeout — without it, a missing response hangs the saga forever.
Event Sourcing PATTERN

Store state as a sequence of events (immutable log), not current state. Rebuild state by replaying events.

JavaEvent Sourced Aggregate
public class Order {
    private UUID id;
    private OrderStatus status;
    private List<OrderEvent> events = new ArrayList<>();

    // Command → generates Event → applies Event
    public void place(List<OrderItem> items) {
        apply(new OrderPlacedEvent(id, items, Instant.now()));
    }

    private void apply(OrderPlacedEvent e) {
        this.status = OrderStatus.PLACED;
        events.add(e); // store in event store
    }

    // Rebuild from history
    public static Order reconstitute(List<DomainEvent> history) {
        Order o = new Order();
        history.forEach(o::apply);
        return o;
    }
}

  • Time-travel debugging
  • Event replay
  • Decoupled read/write

❌ Cons

  • Complex to implement
  • Snapshot management
  • Schema evolution hard
  • Query by current state is difficult

Outbox Pattern & Change Data Capture (CDC) HOT

Atomically save business data AND event to same DB (outbox table), then relay events asynchronously. Solves the dual-write problem.

JavaOutbox Pattern implementation
@Transactional
public Order createOrder(CreateOrderRequest req) {
    Order order = orderRepo.save(new Order(req));

    // Atomically write event to same transaction
    outboxRepo.save(OutboxEvent.builder()
        .aggregateType("Order")
        .aggregateId(order.getId().toString())
        .eventType("OrderPlaced")
        .payload(json.serialize(order))
        .build());

    return order;
}
// Debezium CDC reads outbox table changes → Kafka automatically
🎯
Why Outbox beats dual-write
Dual-write (save to DB, then publish to Kafka) risks: DB committed but Kafka fails → inconsistency. Outbox pattern uses a single ACID transaction for both. Debezium reads the outbox via CDC (WAL) to publish reliably.

Distributed Transactions & Two-Phase Commit (2PC) HOT

2PC uses a coordinator to synchronize commit/rollback across multiple participants. It looks elegant but fails badly in microservices — avoid it.

⚠️ 2PC Problems

  • Blocking protocol — coordinator crash leaves participants locked forever
  • Single point of failure — coordinator is a bottleneck
  • Network partitions — CAP theorem: can't be both consistent AND available
  • Tight coupling — all participants must be available simultaneously
  • Low throughput — 2 round-trips minimum per commit

✅ Microservices Alternative

  • Saga Pattern — choreography or orchestration with compensating transactions
  • Outbox Pattern — atomically write to DB + event table in one local TX
  • Idempotent consumers — at-least-once delivery with dedup
  • Eventual consistency — accept that state converges, don't fight it
⚡
Interview Rule: "We never use 2PC across services. It violates the autonomy principle and has poor failure modes. We use Saga + Outbox instead, accepting eventual consistency."

Cascading Failures & Graceful Degradation
Cascading Failure

Service A → B → C. C is slow → B's threads fill up → A's threads fill up → system-wide outage.

Prevention: Circuit breaker, bulkhead, timeouts, async communication.

Graceful Degradation

Return partial/cached/default response when a dependency fails. Never fail hard to the user.

Distributed Locks

When multiple service instances race to execute the same operation (cron job, inventory reservation), use a distributed lock to ensure only one wins at a time.

// Redisson — distributed lock with lease time
@Service
public class InventoryService {
    private final RedissonClient redisson;

    public void reserveStock(String productId, int qty) {
        RLock lock = redisson.getLock("inventory-lock:" + productId);
        try {
            // wait up to 5s to acquire, auto-release after 10s
            boolean acquired = lock.tryLock(5, 10, TimeUnit.SECONDS);
            if (!acquired) throw new LockAcquisitionException("Could not acquire lock");
            // critical section — safe to read+write inventory
            doReserve(productId, qty);
        } finally {
            if (lock.isHeldByCurrentThread()) lock.unlock();
        }
    }
}

✅ Best Practices

  • Always set a lease/TTL — prevents dead locks on crash
  • Use Redlock for multi-node Redis HA
  • Lock on entity ID, not global — maximize parallelism
  • Keep critical section short — <100ms ideally

⚠️ Alternatives

  • Optimistic Locking — DB version column, retry on conflict
  • DB SELECT FOR UPDATE — for single-DB scenarios
  • Kafka partition key — same key always → same consumer = natural serialization

Common Interview Questions & Model Answers HOT

Q: How do you handle a transaction across 3 microservices?

A: Use the Saga pattern. For choreography: each service publishes events and listens for events from others, with compensating transactions on failure. For orchestration: a central Saga orchestrator (e.g., Temporal) drives each step. Avoid distributed 2PC — it creates tight coupling and doesn't scale.

Q: Service A publishes to Kafka but sometimes the DB commit succeeds and Kafka fails — what do you do?

A: Use the Outbox Pattern. Write to an outbox_events table in the same DB transaction as the business data. A CDC process (Debezium) reads the WAL and publishes to Kafka reliably. This eliminates the dual-write problem.

Q: How do you prevent a slow downstream service from taking down your service?

A: Layer of defenses: Timeout (fail fast) → Retry with backoff+jitter (transient errors) → Circuit Breaker (open when too many failures) → Bulkhead (isolate thread pools) → Fallback (cached/default response). Use Resilience4j in Spring Boot.

Q: How do services find each other?

A: Client-side: service queries Eureka registry, picks instance, load-balances itself (Spring Cloud LoadBalancer). Server-side: Kubernetes Services + kube-proxy route traffic, service just calls by DNS name (http://inventory-service). In K8s, prefer server-side — simpler.

Q: How do you trace a request across 10 services?

A: Distributed tracing with OpenTelemetry. Each request gets a traceId propagated via HTTP headers (traceparent). Each service creates child spans. Spans sent to Jaeger/Zipkin. Micrometer Tracing + Spring Boot 3 auto-instruments. Correlate with logs via traceId in MDC.

💳 Scenario C: Payment Processing Platform HOT

Design a Stripe-like payment platform: accept payments, issue refunds, handle webhooks, maintain ledger consistency.

Idempotency Key Pattern

Client sends Idempotency-Key: UUID header. Server stores (key, response) in a dedup table. On retry with same key, return cached response without re-executing. Prevents double-charges on network retries.

Immutable Double-Entry Ledger

Never UPDATE balance rows. Every transaction = two INSERT rows (debit + credit). Balance = SUM of all entries. Immutability enables audit trail, replay, and point-in-time queries.

Strong Consistency — No Exceptions

Account balance must be consistent. Use PostgreSQL SERIALIZABLE isolation for balance reads during charge. Never use eventual consistency for financial state — dual charge is a critical bug.

🔄 Scenario E: Migrating a Monolith to Microservices HOT

You have a 5-year-old Spring Boot monolith (2M lines). Team has grown to 50 engineers. How do you migrate?

📌
4-Step Migration Framework
1. Assess current pain (deployment speed, team coupling, scaling bottleneck) → 2. Identify high-value extraction candidates (fast-changing, independent-scalable modules) → 3. Propose extraction order (leaf dependencies first, high-value second) → 4. Strangler Fig Pattern — proxy traffic at the edge, route incrementally to new service.

1. Modularize firstSplit monolith into well-defined internal modules (no cross-module direct calls)Zero deployment risk; easier to extract later

Never do a Big Bang rewrite
A parallel rewrite of the entire monolith takes 18+ months, the target keeps moving, and both systems rot. Strangler Fig is incrementally safe and maintains business value throughout. Extract one service at a time.
🏢 Scenario F: Multi-Tenant SaaS Platform PATTERN

Design a SaaS product (like Salesforce, Slack) that serves multiple enterprise tenants with data isolation.

Isolation ModelHowProsCons
Silo (dedicated)Separate DB + infra per tenantStrongest isolation; easy compliance; tenant-sized scalingExpensive; hard to manage at scale; slow provisioning

Runtime Tenant Isolation

Set tenant_id in thread-local at request entry (JWT claim or header). Apply as Hibernate filter or row-level security in DB. NEVER pass tenant_id through 10 layers of service — propagate via context.

Noisy Neighbor Problem

One tenant's heavy usage slows others. Mitigation: per-tenant rate limiting at API Gateway level, per-tenant query quota in DB, or upgrade noisy tenants to Silo model.

Data Migration Safety

Schema changes must be backward-compatible (add-only, never drop). Use Flyway/Liquibase with tenant-aware migration. Never run a migration on all tenant schemas simultaneously — batch with rate limiting.

Hard vs Soft Dependencies

Hard: cannot complete user request without this service (e.g., auth). Soft: can degrade gracefully (e.g., recommendations, notifications). Always know which category each downstream falls into before an incident.

Circuit Breaker + Fallback Together

CB stops the bleeding (no more calls to downed service). Fallback determines the user experience: queue the request, return cached, or show a clear error. Never combine CB with no fallback — you get silent data loss.
