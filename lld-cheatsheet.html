OOP Fundamentals

LLD interviews test whether you can translate real-world requirements into clean, extensible object-oriented code. Master these four pillars — they underpin every design pattern.

The Four Pillars

🔒 Encapsulation

Bundle data + behaviour. Hide internal state. Control access via a well-defined interface.

// BAD: public fields
class BankAccount { public double balance; }

// GOOD: encapsulated
class BankAccount {
  private double balance;
  public void deposit(double amt) {
    if (amt <= 0) throw new IllegalArgumentException();
    this.balance += amt;
  }
  public double getBalance() { return balance; }
}
Why: Change internals without breaking callers. Invariants enforced in one place.
🔮 Abstraction

Expose WHAT an object does, hide HOW it does it. Depend on the interface, not the implementation.

interface PaymentGateway {
  boolean charge(String userId, double amount);
  boolean refund(String txnId);
}

// Multiple implementations, same interface
class StripeGateway implements PaymentGateway {...}
class PayPalGateway implements PaymentGateway {...}
class RazorpayGateway implements PaymentGateway {...}
Why: Swap implementations without touching callers. Easy to mock in tests.
🧬 Inheritance

Child class inherits fields + methods from parent. Enables IS-A relationships and code reuse.

abstract class Vehicle {
  protected String id;
  abstract double calculateFare(double km);
  void startEngine() { System.out.println("Vroom"); }
}
class Car extends Vehicle {
  double calculateFare(double km) { return km * 12.0; }
}
class Bike extends Vehicle {
  double calculateFare(double km) { return km * 8.0; }
}
Pitfall: Deep hierarchies = tight coupling. Prefer composition when in doubt.
🌀 Polymorphism

Same interface, different behaviour. Runtime polymorphism (overriding) vs compile-time (overloading).

// Runtime polymorphism
Vehicle v = new Car();
v.calculateFare(10); // → Car's version at runtime

// Single method works for ANY Vehicle
void printFare(Vehicle v, double km) {
  System.out.println(v.getClass().getSimpleName()
    + ": ₹" + v.calculateFare(km));
}
// Overloading (compile-time)
int add(int a, int b)    { return a+b; }
double add(double a, double b) { return a+b; }
Why: Write general code that works for all subtypes. Add new types without changing existing code (OCP).

Beyond the 4 Pillars

Composition vs Inheritance
// INHERITANCE (wrong)
class Stack extends ArrayList {
  // exposes add(), remove(), get()!
}

// COMPOSITION (right)
class Stack {
  private ArrayList<E> list;
  void push(E e) { list.add(e); }
  E pop() { return list.remove(list.size()-1); }
  // Only exposes what's needed
}
Rule: IS-A → inherit. HAS-A or wants to restrict → compose.
Law of Demeter
// VIOLATION (train wreck)
order.getCustomer()
     .getAddress()
     .getCity(); // talks to strangers

// BETTER (tell, don't ask)
order.getCustomerCity(); // delegate internally

// Each unit should have limited
// knowledge about other units.
// "Only talk to your direct friends."
Tell, Don't Ask
// ASK (bad) — asking state then deciding
if (account.getBalance() > amount) {
  account.debit(amount);
}

// TELL (good) — let object decide
account.debit(amount); // throws if insufficient

// Objects should be responsible
// for their own behaviour.
Interview tip: When asked "what is OOP?", don't just list the 4 pillars. Show you understand the design goal: managing complexity through modularity, encapsulation of change, and the power of polymorphism to write open/extensible code.

SOLID Principles

Mnemonic: Small classes, Open doors, Liskov promises, Interface diets, Depend up. Every SOLID principle has a pattern that implements it.
S — Single Responsibility Principle

A class should have exactly one reason to change

If a class handles both business logic AND data persistence AND formatting, it has 3 reasons to change. Split it.

// BAD: one class does everything
class Report {
  List<Sale> fetchSalesData() {...}    // DB access
  double calculateRevenue() {...}      // business logic
  String formatHTML() {...}            // formatting
  void sendByEmail() {...}             // transport
}

// GOOD: each class has one concern
class SalesRepository  { List<Sale> fetchSalesData() {...} }
class RevenueCalculator { double calculate(List<Sale> s) {...} }
class ReportFormatter   { String formatHTML(Report r) {...} }
class EmailService      { void send(String to, String body) {...} }
Pattern: Service decomposition
O — Open/Closed Principle

Open for extension, closed for modification

Add new behaviour by adding new code, not changing existing code. Implemented via polymorphism.

// BAD: adding new shape requires modifying AreaCalculator
class AreaCalculator {
  double area(Object shape) {
    if (shape instanceof Circle) { ... }
    else if (shape instanceof Rectangle) { ... }
    // Must edit this class for every new shape!
  }
}

// GOOD: add new shape = add new class, nothing changes
interface Shape { double area(); }
class Circle implements Shape { double area() { return Math.PI*r*r; } }
class Rectangle implements Shape { double area() { return w*h; } }
class Triangle implements Shape { double area() { return 0.5*b*h; } }
// AreaCalculator.sum(shapes) never needs to change!
Pattern: Strategy, Observer, Factory Method
L — Liskov Substitution Principle

Subtypes must be substitutable for their base types

If S extends T, wherever T is used, S must work correctly without callers knowing. Classic violation: Square extends Rectangle.

// VIOLATION: Square extends Rectangle
class Rectangle { void setWidth(int w); void setHeight(int h); }
class Square extends Rectangle {
  void setWidth(int w) { this.w = this.h = w; } // breaks Rectangle contract!
}
void test(Rectangle r) {
  r.setWidth(5); r.setHeight(4);
  assert r.area() == 20; // FAILS for Square (gets 16)!
}

// FIX: both implement Shape
interface Shape { double area(); }
class Rectangle implements Shape { ... }
class Square implements Shape { ... }

// LSP rules: subtypes must:
// - Accept same or wider input parameters
// - Return same or narrower output
// - Not throw new exception types
// - Not strengthen preconditions
// - Not weaken postconditions
Pattern: Always think "can caller tell the difference?"
I — Interface Segregation Principle

Clients should not depend on methods they don't use

Fat interfaces force implementors to implement irrelevant methods (empty or throw). Split them.

// BAD: fat interface
interface Worker {
  void work(); void eat(); void sleep();
}
class Robot implements Worker {
  void work() { ... }
  void eat() { throw new UnsupportedOperationException(); } // robots don't eat!
  void sleep() { throw new UnsupportedOperationException(); }
}

// GOOD: segregated interfaces
interface Workable { void work(); }
interface Eatable  { void eat();  }
interface Sleepable { void sleep(); }
class Human implements Workable, Eatable, Sleepable { ... }
class Robot implements Workable { void work() { ... } }
Pattern: Multiple focused interfaces over one fat interface
D — Dependency Inversion Principle

High-level modules should not depend on low-level modules. Both should depend on abstractions.

// BAD: high-level depends on low-level concrete
class OrderService {
  private MySQLDatabase db = new MySQLDatabase(); // tightly coupled!
  void placeOrder(Order o) { db.save(o); }
}

// GOOD: both depend on abstraction
interface OrderRepository { void save(Order o); }
class MySQLOrderRepository implements OrderRepository { ... }
class MongoOrderRepository implements OrderRepository { ... }

class OrderService {
  private final OrderRepository repo; // depends on abstraction
  OrderService(OrderRepository repo) { this.repo = repo; } // INJECTION
  void placeOrder(Order o) { repo.save(o); }
}
// Swap DB without touching OrderService!
// Spring @Autowired implements this via IoC container
Pattern: Dependency Injection, IoC Container

LLD Interview Framework

AlgoMaster LLD interviews follow a predictable arc. Master this framework to stay structured under pressure.

The 45-Minute Arc

⏱ 0–5 min: Clarify
  • What actors/users are involved?
  • What are the core use cases? (3-5)
  • Any obvious constraints? (concurrency, scale)
  • Which features are in/out of scope?

"Before I design, let me confirm the core use cases..."

⏱ 5–15 min: Entities
  • Identify nouns → classes
  • Identify verbs → methods
  • Draw relationships (IS-A, HAS-A)
  • Define enums for status/type fields

"The key entities I see are..."

⏱ 15–35 min: Class Design
  • Write key class skeletons
  • Identify patterns that apply
  • Handle edge cases (concurrency, null)
  • Show extensibility

"Let me start with the core service class..."

⏱ 35–40 min: Patterns & Justification
  • Name the patterns you used and WHY
  • "I used Strategy here because the algorithm varies..."
  • "I used Singleton for the controller because..."
  • Mention what SOLID principles you followed
⏱ 40–45 min: Extensions
  • Propose concurrency fixes if relevant
  • Mention how to make it distributed
  • Walk through a new use case: "If we added feature X..."
  • Ask if they want to drill into anything

Class Design Template

// Step 1: Enums for all states/types
enum Status { ACTIVE, INACTIVE, PENDING }

// Step 2: Core entity classes (nouns from requirements)
class Entity {
  String id;               // always have an ID
  Status status;           // always model states as enum
  LocalDateTime createdAt; // timestamps matter
  // relationships: composition (private field) or association (id reference)
}

// Step 3: Core service class
class EntityService {
  private final EntityRepository repo;       // DIP: depend on interface
  private final NotificationService notify;  // separate concerns
  
  EntityService(EntityRepository r, NotificationService n) { ... } // DI
  
  Entity create(CreateRequest req) {
    validate(req);          // validation first
    Entity e = map(req);    // map DTO to entity
    repo.save(e);           // persist
    notify.send(e);         // side effects after
    return e;
  }
}

// "I used Repository pattern to decouple persistence"
// "I used Observer for notifications"
// "I'd add Strategy for pricing variations"

Creational Patterns (5)

Creational patterns deal with HOW objects are created. They decouple the creation process from the class itself, giving you control over what gets created, who creates it, and when.
Mnemonic — BAFPS: Build it step-by-step, Abstract the factory, Factory lets subclass decide, Prototype clones, Singleton is one.
CREATIONAL

1. Singleton — One Instance

Problem: Need exactly one instance (Config, DB pool, Cache). Intent: Ensure only one instance exists; provide global access point.

classDiagram class Singleton { -static Singleton instance -Singleton() +static getInstance() Singleton +getConnection() Connection } Singleton --> Singleton : creates once 
// BEST: Enum Singleton (thread-safe, serialization-safe, reflection-safe)
enum AppConfig {
  INSTANCE;
  private final Properties props = loadProps();
  public String get(String key) { return props.getProperty(key); }
}
// Usage: AppConfig.INSTANCE.get("db.url")

// ALTERNATIVE: Double-checked locking (when Enum won't work)
class ConnectionPool {
  private static volatile ConnectionPool instance; // volatile prevents reorder
  private ConnectionPool() {}
  public static ConnectionPool getInstance() {
    if (instance == null) {                    // 1st check (no lock)
      synchronized (ConnectionPool.class) {
        if (instance == null) {               // 2nd check (with lock)
          instance = new ConnectionPool();
        }
      }
    }
    return instance;
  }
}

// STATIC HOLDER (lazy + thread-safe without volatile)
class Registry {
  private static class Holder { static final Registry INSTANCE = new Registry(); }
  public static Registry getInstance() { return Holder.INSTANCE; }
}
When: Config, Logger, Thread pools, Hardware device drivers, DB connection pool. Avoid: Over-using it — global state makes testing hard.
CREATIONAL

2. Factory Method — Subclass Decides

Problem: Framework needs to create objects but doesn't know which concrete class to use. Intent: Define interface for creating objects; let subclasses decide which class to instantiate.

classDiagram class Notification { +send(String msg) } class EmailNotification { +send(String msg) } class SMSNotification { +send(String msg) } class NotificationFactory { +createNotification(type) Notification } Notification <|-- EmailNotification Notification <|-- SMSNotification NotificationFactory ..> Notification : creates 
interface Notification { void send(String msg); }
class EmailNotification implements Notification { ... }
class SMSNotification   implements Notification { ... }
class PushNotification  implements Notification { ... }

class NotificationFactory {
  public static Notification create(String type) {
    return switch (type) {
      case "EMAIL" -> new EmailNotification();
      case "SMS"   -> new SMSNotification();
      case "PUSH"  -> new PushNotification();
      default -> throw new IllegalArgumentException("Unknown: " + type);
    };
  }
}
// Usage (client doesn't know concrete class)
Notification n = NotificationFactory.create("EMAIL");
n.send("Your order is placed!");
When: Creating objects whose type is determined at runtime, multiple product types share interface.
CREATIONAL

3. Abstract Factory — Family of Objects

Problem: Need to create families of related objects (e.g., all Windows UI or all Mac UI) without specifying concrete classes. Intent: Factory of factories.

// Family: Button + Checkbox (must be from same OS)
interface Button   { void render(); }
interface Checkbox { void render(); }

class WinButton   implements Button   { void render() { /*Win style*/} }
class MacButton   implements Button   { void render() { /*Mac style*/} }
class WinCheckbox implements Checkbox { void render() { /*Win style*/} }
class MacCheckbox implements Checkbox { void render() { /*Mac style*/} }

interface UIFactory {
  Button   createButton();
  Checkbox createCheckbox();
}
class WindowsUIFactory implements UIFactory {
  Button   createButton()   { return new WinButton(); }
  Checkbox createCheckbox() { return new WinCheckbox(); }
}
class MacUIFactory implements UIFactory {
  Button   createButton()   { return new MacButton(); }
  Checkbox createCheckbox() { return new MacCheckbox(); }
}
// Client gets the factory, never touches concrete classes
UIFactory factory = new MacUIFactory(); // or WindowsUIFactory
Button btn = factory.createButton(); // always consistent family
When: UI toolkits, Cloud provider SDKs (AWS vs GCP), DB driver families.
CREATIONAL

4. Builder — Complex Object Construction

Problem: Constructor with many optional parameters (telescoping constructor anti-pattern). Intent: Separate complex construction from representation; build step-by-step.

// Telescoping anti-pattern:
new Pizza("large","thin",true,false,true,false,"mushrooms")
// Which arg is which?!

// Builder pattern
class Pizza {
  private final String size, crust, topping;
  private final boolean cheese, pepperoni, mushrooms;
  
  private Pizza(Builder b) {
    this.size = b.size; this.crust = b.crust;
    this.cheese = b.cheese; this.mushrooms = b.mushrooms;
    this.topping = b.topping;
  }
  
  public static class Builder {
    // required
    private final String size, crust;
    // optional (with defaults)
    private boolean cheese = false;
    private boolean mushrooms = false;
    private String topping = "";
    
    public Builder(String size, String crust) { this.size=size; this.crust=crust; }
    public Builder cheese()  { this.cheese=true; return this; }  // fluent
    public Builder mushrooms() { this.mushrooms=true; return this; }
    public Builder topping(String t) { this.topping=t; return this; }
    public Pizza build() { return new Pizza(this); }
  }
}
// Clean, readable, no positional confusion
Pizza p = new Pizza.Builder("large","thin").cheese().topping("mushrooms").build();
When: Object has many optional fields, construction order matters, immutable objects. Real examples: HttpRequest.Builder, StringBuilder, Lombok @Builder.
CREATIONAL

5. Prototype — Clone Objects

Problem: Object creation is expensive; need many similar objects. Intent: Create new objects by copying (cloning) an existing prototype.

interface Cloneable { Shape clone(); }

abstract class Shape {
  String color;
  abstract Shape clone();
}
class Circle extends Shape {
  int radius;
  Circle(Circle other) { this.color = other.color; this.radius = other.radius; } // copy ctor
  Shape clone() { return new Circle(this); }
}

// Registry — lookup and clone configured prototypes
class ShapeRegistry {
  private Map<String, Shape> registry = new HashMap<>();
  void register(String key, Shape s) { registry.put(key, s); }
  Shape get(String key) { return registry.get(key).clone(); } // returns copy!
}
// Client
ShapeRegistry reg = new ShapeRegistry();
reg.register("small-red-circle", new Circle("red", 5));
Shape s1 = reg.get("small-red-circle"); // clone, don't create from scratch
Shape s2 = reg.get("small-red-circle"); // different instance, same config
When: Object creation is expensive (DB read, network call), many similar objects needed. Real: Integer.valueOf() caches -128 to 127, String pool.

Structural Patterns (7)

Structural patterns deal with HOW classes and objects are composed. They enable you to build larger structures from smaller parts while keeping them flexible.
Mnemonic — ABCDFPP: Adapter converts, Bridge decouples, Composite tree, Decorator wraps, Facade simplifies, Proxy controls, Piggyback Flyweight shares.
STRUCTURAL

1. Adapter — Incompatible → Compatible

Problem: Existing class has the right logic but wrong interface. Can't change the class. Intent: Wrap an object to translate its interface into one clients expect.

classDiagram class MediaPlayer { +play(type, file) } class AdvancedPlayer { +playVlc(file)\n+playMp4(file) } class MediaAdapter { -AdvancedPlayer player +play(type, file) } MediaPlayer <|.. MediaAdapter MediaAdapter --> AdvancedPlayer 
// Existing legacy class (can't change)
class LegacyPaymentSystem {
  void processPayment(int amountInPaisa, long accountNum) { ... }
}
// New expected interface
interface PaymentGateway { void pay(double amountInRupees, String userId); }

// Adapter bridges them
class LegacyPaymentAdapter implements PaymentGateway {
  private LegacyPaymentSystem legacy = new LegacyPaymentSystem();
  public void pay(double rupees, String userId) {
    int paisa = (int)(rupees * 100);
    long account = Long.parseLong(userId);
    legacy.processPayment(paisa, account); // translates call
  }
}
When: Integrating third-party libs, legacy code migration. Real: Arrays.asList(), InputStreamReader(InputStream).
STRUCTURAL

2. Decorator — Add Behaviour at Runtime

Problem: Want to add responsibilities to objects individually without subclassing (which creates combinatorial explosion). Intent: Wrap objects with same interface; each decorator adds one feature.

class SimpleCoffee implements Coffee {

  public double getCost() { return 50.0; }
}
abstract class CoffeeDecorator implements Coffee {
  protected Coffee coffee;

  MilkDecorator(Coffee c) { super(c); }

Real Java: new BufferedReader(new InputStreamReader(new FileInputStream("f"))). When: Adding optional features to objects, when subclassing causes class explosion.
STRUCTURAL

3. Proxy — Control Access

Problem: Need to control access to an object (security, lazy init, caching, logging). Intent: Provide a surrogate with the same interface; add behaviour without changing the real object.

// Types of Proxy:
// Virtual Proxy: lazy initialization
class HeavyImageProxy implements Image {
  private String path; private HeavyImage real;
  public void display() {
    if (real == null) real = new HeavyImage(path); // load only when needed
    real.display();
  }
}
// Protection Proxy: access control
class SecureDataProxy implements DataService {
  private DataService real; private AuthService auth;
  public Data getData(String userId) {
    if (!auth.hasPermission(userId, "READ")) throw new AccessDeniedException();
    return real.getData(userId);
  }
}
// Caching Proxy: memoize
class CachingProxy implements WeatherService {
  private WeatherService real; private Map<String, Weather> cache = new HashMap<>();
  public Weather getWeather(String city) {
    return cache.computeIfAbsent(city, c -> real.getWeather(c));
  }
}
// Spring AOP uses dynamic proxy for @Transactional, @Cacheable, @Secured
When: Lazy loading expensive resources, access control, logging/monitoring, caching.
STRUCTURAL

4. Facade — Simplify Complex Subsystem

Problem: Complex subsystem with many classes is hard to use. Intent: Provide a simple, high-level interface to a complex subsystem.

// Complex subsystem
class VideoEncoder { void encode(String file, String format) {...} }
class AudioMixer   { void mix(String file, int volume) {...} }
class BitrateSelector { String select(String quality) {...} }
class ThumbnailGenerator { void generate(String file) {...} }

// Facade — hides all complexity
class VideoConversionFacade {
  private VideoEncoder encoder = new VideoEncoder();
  private AudioMixer mixer = new AudioMixer();
  private BitrateSelector selector = new BitrateSelector();
  private ThumbnailGenerator thumbGen = new ThumbnailGenerator();
  
  public String convertVideo(String file, String format) {
    String bitrate = selector.select("high");
    encoder.encode(file, format);
    mixer.mix(file, 100);
    thumbGen.generate(file);
    return file.replace(".avi", "." + format);
  }
}
// Client uses ONE simple method instead of 4+ classes
When: Simplifying complex APIs, hiding legacy subsystems, defining entry points to layers. Real: Spring's JdbcTemplate, HttpClient.
STRUCTURAL

5. Composite — Tree of Objects

Problem: Need to treat individual objects and groups of objects uniformly. Intent: Compose objects into tree structures; leaf and container share same interface.

interface FileSystemItem {
  String getName(); long getSize(); void print(String indent);
}
class File implements FileSystemItem {
  private String name; private long size;
  public long getSize() { return size; }
  public void print(String indent) { System.out.println(indent + name + " (" + size + ")"); }
}
class Directory implements FileSystemItem {
  private String name; private List<FileSystemItem> children = new ArrayList<>();
  public void add(FileSystemItem item) { children.add(item); }
  public long getSize() { return children.stream().mapToLong(FileSystemItem::getSize).sum(); }
  public void print(String indent) {
    System.out.println(indent + name + "/");
    children.forEach(c -> c.print(indent + "  "));
  }
}
// Client treats File and Directory identically!
FileSystemItem root = new Directory("root");
root.add(new File("readme.txt", 100));
root.add(new File("app.jar", 5000));
FileSystemItem src = new Directory("src");
src.add(new File("Main.java", 300));
root.add(src);
root.print("");
When: Part-whole hierarchies (file system, UI components, org charts, XML/JSON DOM). Real: java.awt.Component, JUnit test suites.
STRUCTURAL

6. Bridge — Decouple Abstraction from Implementation

Problem: Two orthogonal dimensions of change cause class explosion (e.g., 3 shapes × 3 colors = 9 classes). Intent: Put the two dimensions in separate hierarchies and compose them.

// Without Bridge: CircleRed, CircleBlue, RectangleRed, RectangleBlue... (M×N)
// With Bridge: M shapes + N renderers = M+N classes

interface Renderer { void renderCircle(double r); void renderRect(double w, double h); }
class VectorRenderer implements Renderer { /* draw vector shapes */ }
class RasterRenderer implements Renderer { /* draw pixel shapes */ }

abstract class Shape {
  protected Renderer renderer; // bridge to implementation
  Shape(Renderer r) { this.renderer = r; }
  abstract void draw();
}
class Circle extends Shape {
  double radius;
  Circle(double r, Renderer renderer) { super(renderer); this.radius = r; }
  void draw() { renderer.renderCircle(radius); }
}
// Mix and match:
new Circle(5, new VectorRenderer()).draw();
new Circle(5, new RasterRenderer()).draw();
When: Two orthogonal class hierarchies, platform-independent code. vs Adapter: Bridge is designed upfront; Adapter is a retrofit for incompatibility.
STRUCTURAL

7. Flyweight — Share Common State

Problem: Too many objects consuming too much memory because most of their state is duplicated. Intent: Share INTRINSIC state; pass EXTRINSIC state in from outside.

// Intrinsic (shared, stored in flyweight): species, colour, mesh data
// Extrinsic (unique per object, passed in): position, health

class TreeType { // Flyweight
  String name, color, texture; // intrinsic (shared by all trees of this type)
  void draw(int x, int y) { /* draw at position x,y */ } // x,y = extrinsic
}
class TreeTypeFactory {
  private static Map<String, TreeType> pool = new HashMap<>();
  static TreeType get(String name, String color, String texture) {
    return pool.computeIfAbsent(name+color+texture,
      k -> new TreeType(name, color, texture));
  }
}
class Tree { // Context — tiny, many instances
  int x, y; TreeType type; // reference to shared flyweight
  Tree(int x, int y, String n, String c, String t) {
    this.x=x; this.y=y; this.type = TreeTypeFactory.get(n, c, t);
  }
  void draw() { type.draw(x, y); }
}
// 1M trees but only 5 TreeType objects in memory!

  InOrderIterator(Node<T> root) { pushLeft(root); }

⚖️ Pattern Comparisons — Confused Pairs

These are the most commonly confused patterns in LLD interviews. Know the KEY differentiator for each pair.

Creational: Factory vs Builder vs Prototype

Factory Method vs Abstract Factory

Factory Method

  • ONE product type
  • Subclass decides which concrete class
  • Override a single create() method
  • Example: NotificationFactory.create("EMAIL")

Abstract Factory

  • FAMILIES of related products
  • All products must be compatible (e.g. same OS)
  • Override an entire factory interface
  • Example: UIFactory creates Button+Checkbox+TextField
🎯 Key differentiator: Need ONE type? → Factory Method. Need a whole family that belongs together? → Abstract Factory.
Factory Method vs Builder

Factory Method

  • Simple creation, one step
  • Type chosen at runtime
  • All params known upfront
  • Returns polymorphic type

Builder

  • Complex creation, multi-step
  • Many optional parameters
  • Fluent API for readable setup
  • Returns one specific type (immutable)
🎯 Key differentiator: Choosing the type? → Factory. Many optional params / complex init? → Builder.

Structural: Adapter vs Facade vs Decorator vs Proxy

All Four Wrap Objects — What's the Difference?
PatternIntentChanges Interface?When
AdapterConvert incompatible interface to expected one✅ YES — translates interfaceLegacy code, 3rd party libs
DecoratorAdd new behaviour, keep same interface❌ NO — same interfaceOptional features, runtime composition
ProxyControl access to object, keep same interface❌ NO — same interfaceLazy init, security, caching, logging
FacadeSimplify multiple classes into one interface✅ YES — new simpler interfaceComplex subsystems, layered architecture
🎯 Key differentiator: Incompatibility? Adapter. Add features? Decorator. Control access? Proxy. Simplify many? Facade.
Decorator vs Inheritance

Inheritance

  • Static (compile time)
  • N features → 2^N subclasses (Coffee: Milk, Sugar, Caramel = 8 classes)
  • Can't combine at runtime
  • Simple hierarchies

Decorator

  • Dynamic (runtime)
  • N decorators → N classes, infinite combos
  • Stack decorators in any order
  • Same interface as wrapped
🎯 Key differentiator: Need runtime combinations? → Decorator. Simple fixed extension? → Inheritance.

Behavioral: Strategy vs State vs Template Method

Strategy vs State

Strategy

  • Client explicitly swaps algorithm
  • Strategies are stateless
  • No knowledge of each other
  • Context doesn't change based on strategy
  • Example: sorting algorithm, pricing

State

  • State transitions happen internally
  • States know about each other (they trigger transitions)
  • Context behavior changes as state changes
  • State object changes the context's state
  • Example: order lifecycle, ATM
🎯 Key differentiator: WHO controls switching? Client → Strategy. Object transitions itself internally → State.
Strategy vs Template Method

Strategy

  • Uses composition
  • Full algorithm in separate class
  • Swap entire algorithm
  • More flexible, preferred (no inheritance)

Template Method

  • Uses inheritance
  • Skeleton in base class, steps in subclass
  • Algorithm order locked (final method)
  • Simpler when algorithm structure rarely changes
🎯 Key differentiator: Composition wanted / full algorithm varies? → Strategy. Inheritance OK / only steps vary? → Template Method.
Observer vs Mediator

Observer

  • Subject broadcasts to ALL observers
  • Subject doesn't know what observers do
  • Simple 1-to-N notification
  • Observers are decoupled from each other
  • Example: EventBus, Kafka topic

Mediator

  • Central hub ROUTES to specific recipients
  • Mediator knows about all participants
  • Smart M-to-N coordination
  • Participants are decoupled from each other
  • Example: Chat room, Air traffic control
🎯 Key differentiator: Broadcast to all? → Observer. Smart routing / coordination? → Mediator.
Command vs Strategy

Command

  • Encapsulates WHAT to do (the request)
  • Supports undo/redo
  • Can be queued, logged, scheduled
  • Has execute() + undo()
  • About deferred execution

Strategy

  • Encapsulates HOW to do it (the algorithm)
  • No undo concept
  • Executed immediately when selected
  • Has one method: execute()/sort()/calculate()
  • About algorithm variation
🎯 Key differentiator: Need undo/queue/log the action? → Command. Just swapping algorithm? → Strategy.
Chain of Responsibility vs Decorator

Chain of Responsibility

  • Request MAY STOP at any handler
  • Only ONE handler typically processes
  • Handler decides: process or pass
  • Example: Support escalation, auth filter

Decorator

  • Request goes through ALL decorators
  • Each decorator ADDS something
  • All decorators execute (cumulative)
  • Example: IO streams, middleware pipeline
🎯 Key differentiator: Request may stop early? → CoR. All must process? → Decorator.

equals() & hashCode() Contract

// RULE: If equals() true → hashCode() MUST be same.
// If hashCode() same → equals() MAY be false (collision is OK).
// Always use IMMUTABLE fields in equals/hashCode!
class Money {
  private final BigDecimal amount; private final String currency;
  @Override public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof Money)) return false;
    Money m = (Money) o;
    return amount.compareTo(m.amount) == 0 && currency.equals(m.currency);
  }
  @Override public int hashCode() { return Objects.hash(amount, currency); }
}
// 5 rules: Reflexive, Symmetric, Transitive, Consistent, equals(null)=false

🎯 GRASP Principles (9)

GRASP (General Responsibility Assignment Software Patterns) — 9 principles for assigning responsibilities to classes. Complements GoF patterns.
1. Information Expert

Assign responsibility to the class that has the data needed to fulfill it.

"Who knows the order total? Order class does."

class Order {
  // EXPERT: has lineItems
  double getTotal() {
    return lineItems.stream()
      .mapToDouble(LineItem::getSubtotal).sum();
  }
}
2. Creator

Assign object creation to the class that (a) contains, (b) aggregates, (c) closely uses, or (d) has init data for the new object.

"Order creates OrderItems; OrderFactory creates Orders."

3. Controller

Assign system event handling to a Controller class (facade, use-case, or session controller).

"OrderController handles placeOrder(), not Order itself."

4. Low Coupling

Assign responsibilities to minimize dependencies. Fewer dependencies = easier change.

// High coupling: Service knows DB, Cache, Email
// Low coupling: Service depends on interfaces
// Achieved via: DI, interfaces, events
5. High Cohesion

Give a class a focused, related set of responsibilities. Each class = one clear purpose.

Low cohesion = God class doing everything = hard to change.

6. Polymorphism

Use polymorphism instead of if-else type checks. When behaviour varies by type, use polymorphism (OCP).

// Instead of: if (type=="pdf") ... else if (type=="word")
// Use: interface Report { void generate(); }
7. Pure Fabrication

Create a class that doesn't exist in the domain when needed for low coupling / high cohesion. Service classes, DAOs, Utilities.

OrderRepository doesn't map to domain, but gives cohesion to DB ops.

8. Indirection

Introduce an intermediate object to decouple two classes. Message broker, Controller, Adapter.

"Don't call the DB directly; go through a Repository."

9. Protected Variations

Identify points of instability; wrap them in a stable interface. Changes in one part don't ripple through system.

"DB schema changes don't affect Service layer — DAO absorbs the change."

2. LRU Cache — O(1) get & put

class LRUCache {
  private final int cap;
  private final Map<Integer,Node> map = new HashMap<>();
  private final Node head = new Node(0,0), tail = new Node(0,0); // sentinels
  LRUCache(int cap) { this.cap=cap; head.next=tail; tail.prev=head; }
  
  public int get(int key) {
    if (!map.containsKey(key)) return -1;
    moveToFront(map.get(key)); return map.get(key).val;
  }
  public void put(int key, int val) {
    if (map.containsKey(key)) { map.get(key).val=val; moveToFront(map.get(key)); return; }
    if (map.size()==cap) { map.remove(tail.prev.key); remove(tail.prev); }
    Node n = new Node(key,val); map.put(key,n); addFront(n);
  }
  private void moveToFront(Node n) { remove(n); addFront(n); }
  private void remove(Node n) { n.prev.next=n.next; n.next.prev=n.prev; }
  private void addFront(Node n) { n.next=head.next; n.prev=head; head.next.prev=n; head.next=n; }
}

5. Elevator System (SCAN/LOOK Algorithm)

enum Direction { UP, DOWN, IDLE }
class Elevator {
  int id, currentFloor; Direction dir; ElevatorState state;
  TreeSet<Integer> upQ  = new TreeSet<>();           // pending up requests
  TreeSet<Integer> downQ= new TreeSet<>(reverseOrder()); // pending down
  
  void addRequest(int floor) {
    if (floor > currentFloor || dir == UP) upQ.add(floor);
    else downQ.add(floor);
  }
  void step() { // SCAN: serve all in one direction, then reverse
    if (dir == UP && !upQ.isEmpty()) { currentFloor = upQ.first(); upQ.remove(currentFloor); }
    else if (!downQ.isEmpty()) { dir = DOWN; currentFloor = downQ.first(); downQ.remove(currentFloor); }
    else if (!upQ.isEmpty())  { dir = UP;   currentFloor = upQ.first(); upQ.remove(currentFloor); }
    else dir = IDLE;
  }
}

🔑 Key Decision Questions

Composition
Interface vs Abstract Class?
Use Interface when: multiple inheritance needed, contract only (no state), unrelated classes share behavior (Comparable, Serializable)

Use Abstract Class when: share state/code, template method pattern, strong IS-A relationship
// Interface: can implement many class Dog implements Runnable, Comparable<Dog> {} // Abstract: shares code abstract class Vehicle { protected int speed; // shared state abstract void accelerate(); void stop() { speed = 0; } // shared code }
Composition
Composition vs Inheritance?
Favor Composition (HAS-A) when: want to change behavior at runtime, avoid fragile base class, combine multiple behaviors

Use Inheritance (IS-A) when: true IS-A relationship, want polymorphism via type hierarchy, LSP is satisfied
// Composition — flexible class Duck { FlyBehavior fly; // can change at runtime! QuackBehavior quack; void performFly() { fly.fly(); } } // Inheritance — brittle class RubberDuck extends Duck { void fly() { /* can't fly! */ } // violates LSP
Creation
Which Singleton variant?
🥇 Enum: thread-safe, serialization-safe, reflection-safe (Best!)
🥈 Static Holder: lazy + thread-safe via class loading
🥉 DCL + volatile: explicit lazy, JVM-aware
❌ Eager: simple but initializes at class load
// BEST: Enum Singleton enum Config { INSTANCE; public String get(String k) { return props.get(k); } } // Lazy + thread-safe: Static Holder private static class Holder { static final DB INSTANCE = new DB(); } public static DB getInstance() { return Holder.INSTANCE; }
Behavior
Strategy vs State?
Strategy: Client controls which algorithm. Object doesn't know about other strategies. Stateless or per-call state.

State: State transitions are internal. States know about each other (or a context manages). Encapsulates state-dependent behavior.
// Strategy: external control sorter.setStrategy(new QuickSort()); // CLIENT decides // State: internal transitions // VendingMachine changes its own state: class IdleState { void insertCoin(VM vm) { vm.setState(vm.getHasCoinState()); // internal } }
Structure
Decorator vs Proxy vs Adapter?
Decorator: Same interface, adds features, can be stacked, client chooses at runtime
Proxy: Same interface, controls access (lazy/cache/auth), client unaware
Adapter: Different interfaces, no new features, bridges incompatible APIs
// Decorator: new pizza.getPrice() Pizza p = new CheesePizza(new TomatoPizza(base)); // Proxy: client uses IService, unaware of proxy IService s = new CachingProxy(new RealService()); // Adapter: JSONDataSource wraps XMLDataSource DataSource ds = new XMLtoJSONAdapter(xmlSource);
Behavior
Observer vs Mediator?
Observer: One subject → many observers. Observers don't know each other. Simple broadcast. Good for loose coupling.

Mediator: Many objects ↔ one hub. Hub contains all logic. Objects only talk to hub. Good when many-to-many gets complex.
// Observer: Stock → many displays stock.addObserver(phoneDisplay); stock.addObserver(webDisplay); // don't know each other // Mediator: chat room chatRoom.send(alice, "hello"); // hub routes to bob, charlie // alice, bob, charlie don't reference each other

🚧 LLD Traps & How to Avoid Them

Top 15 Interview Traps

Trap #1
God Class Anti-Pattern
❌ One class does everything (UserManager handles auth, profile, billing, email)
✅ Split by Single Responsibility: AuthService, ProfileService, BillingService, EmailService
// BAD class UserManager { void authenticate() {...} void updateProfile() {...} void chargeCard() {...} void sendEmail() {...} } // GOOD — separate by responsibility class AuthService { void authenticate() {...} } class PaymentService { void chargeCard() {...} }
Trap #2
Skipping Enums
❌ Using String constants: "AVAILABLE", "BOOKED" → typo-prone, no exhaustive switch
✅ Use enums for fixed sets of states. They're type-safe, IDE-completable, and work in switch expressions
// BAD String status = "AVALIABLE"; // typo, no compile error! // GOOD enum SeatStatus { AVAILABLE, BOOKED, LOCKED } switch (seat.getStatus()) { case AVAILABLE -> book(seat); case BOOKED -> throw new AlreadyBookedException(); // compiler warns if LOCKED is unhandled! }
Trap #3
Mutable Public Fields
❌ public fields with no encapsulation → any code can corrupt state
✅ private + getters, defensive copies for collections and mutable objects
// BAD public class Booking { public Date checkIn; // mutable, public! public List<Guest> guests; // caller can modify! } // GOOD private Date checkIn; private List<Guest> guests; public Date getCheckIn() { return new Date(checkIn.getTime()); } public List<Guest> getGuests() { return Collections.unmodifiableList(guests); }
Trap #4
Missing equals/hashCode
❌ Default object identity breaks Sets, Maps, and deduplication
✅ Override both (contract: equal objects must have equal hashCode). Use same fields in both.
// BAD: uses object reference Set<User> set = new HashSet<>(); set.add(new User("alice")); set.contains(new User("alice")); // FALSE! // GOOD @Override public boolean equals(Object o) { if (!(o instanceof User)) return false; return email.equals(((User) o).email); } @Override public int hashCode() { return Objects.hash(email); }
Trap #5
Concrete Dependencies
❌ Depending on concrete classes: new MySQLDB() → hard to test, can't swap
✅ Depend on interfaces (DIP). Inject via constructor. Makes testing with mocks trivial.
// BAD class OrderService { MySQLDatabase db = new MySQLDatabase(); // concrete! } // GOOD class OrderService { private final Repository db; // interface! OrderService(Repository db) { this.db = db; } // injected! } // Test: new OrderService(new InMemoryRepository()) // Prod: new OrderService(new MySQLRepository())
Trap #6
Null Returns
❌ Returning null forces callers to null-check everywhere → NullPointerException
✅ Return Optional<T> for "maybe absent", empty collections (not null), or throw checked exceptions
// BAD User find(String id) { return null; } // caller forgets null check User u = repo.find("x"); u.getName(); // NPE! // GOOD Optional<User> find(String id) { return Optional.ofNullable(...); } repo.find("x") .map(User::getName) .orElse("Unknown"); // never NPE // Collections: return empty, never null List<Order> getOrders() { return Collections.emptyList(); }
Trap #7
Primitive Obsession
❌ Using primitives for domain concepts: String for email, int for money
✅ Create Value Objects that encapsulate validation and behavior
// BAD void book(String email, int price, String currency) { ... } // What if price is negative? email invalid? // GOOD - Value Objects class Email { private final String value; Email(String v) { if (!v.contains("@")) throw new IllegalArgumentException(); this.value = v; } } class Money { private final BigDecimal amount; private final Currency currency; Money add(Money other) { ... } }
Trap #8
Over-Engineering / Premature Pattern
❌ Adding Factory/Strategy/Observer for 2-3 simple cases just to "show patterns"
✅ Add patterns when you feel the pain: duplication, rigid conditionals, tight coupling. YAGNI!
// BAD: AbstractFactory for 2 types interface Button {} class WindowsButton implements Button {} class MacButton implements Button {} interface GUIFactory { Button createButton(); } // ... 5 more classes for 2 buttons! // GOOD: Simple factory method is enough Button createButton(OS os) { return os == OS.WINDOWS ? new WindowsButton() : new MacButton(); }
Trap #9
Singleton Abuse
❌ Making everything a Singleton "for convenience" → global state, tight coupling, untestable
✅ Use Singleton only for truly shared resources (config, connection pools). Inject via DI.
// BAD: Singletons everywhere UserService.getInstance().validate(); OrderService.getInstance().create(); // Impossible to test in isolation! // GOOD: Inject dependencies class CheckoutService { CheckoutService(UserService users, OrderService orders) { ... } } // Tests: inject mocks new CheckoutService(mockUsers, mockOrders)
Trap #10
Not Handling Concurrency
❌ Shared mutable state without synchronization → race conditions in multi-threaded LLD
✅ Use volatile for visibility, AtomicX for single-variable ops, synchronized/locks for compound ops
// BAD: Race condition class Counter { int count = 0; } // Thread A: count = count + 1 → reads 0, writes 1 // Thread B: count = count + 1 → reads 0, writes 1 (lost!) // GOOD: AtomicInteger AtomicInteger count = new AtomicInteger(0); count.incrementAndGet(); // atomic read-modify-write // For Singleton: volatile + DCL private static volatile DB instance; if (instance == null) { synchronized (DB.class) { if (instance == null) instance = new DB(); } }
Trap #11
Missing Exceptions
❌ Silent failures: returning false/null when things go wrong → caller can't distinguish success/failure
✅ Use custom exceptions that carry context. Checked for recoverable, unchecked for programming errors.
// BAD boolean book(int seatId) { if (seat == null) return false; // WHY did it fail? if (seat.isBooked()) return false; // same return for diff reasons } // GOOD void book(int seatId) throws SeatNotFoundException, SeatAlreadyBookedException { Seat seat = repo.find(seatId) .orElseThrow(() -> new SeatNotFoundException(seatId)); if (seat.isBooked()) throw new SeatAlreadyBookedException(seatId); seat.book(); }
Trap #12
Anemic Domain Model
❌ Domain objects are pure data bags (just getters/setters). All logic in service classes.
✅ Put behavior where the data is. "Tell, Don't Ask." Rich domain model with methods that enforce invariants.
// BAD: Anemic class Order { double total; List<Item> items; /* only getters/setters */ } class OrderService { void applyDiscount(Order o) { o.setTotal(o.getTotal() * 0.9); } } // GOOD: Rich model class Order { private double total; void applyDiscount(double pct) { if (pct < 0 || pct > 1) throw new IllegalArgumentException(); this.total *= (1 - pct); // enforces invariant } }
Trap #13
Breaking LSP Silently
❌ Subclass narrows behavior (throws UnsupportedOperationException) or weakens postconditions
✅ Ask: "Can I always substitute the subtype for the parent without breaking the program?" Square→Rectangle fails this.
// BAD: Square violates LSP class Rectangle { setWidth(w); setHeight(h); } class Square extends Rectangle { // Must set both: breaks parent contract! void setWidth(int w) { super.setWidth(w); super.setHeight(w); } } // Client: r.setWidth(5); r.setHeight(3); → area should be 15 // But if r is Square: area = 9! LSP violated // FIX: Don't inherit Square from Rectangle // Use separate classes or Shape interface
Trap #14
Circular Dependencies
❌ A depends on B, B depends on A → can't compile, can't test, can't understand
✅ Introduce interface/event to break the cycle. One should depend on an abstraction the other implements.
// BAD: Circular class OrderService { PaymentService payment; } class PaymentService { OrderService order; } // cycle! // GOOD: Break with interface interface OrderEventListener { void onOrderPlaced(Order o); } class OrderService { List<OrderEventListener> listeners; } class PaymentService implements OrderEventListener { void onOrderPlaced(Order o) { processPayment(o); } } // PaymentService no longer holds OrderService!
Trap #15
Forgetting Thread Safety in Singleton
❌ Lazy Singleton without synchronization → two threads can create two instances
✅ Use Enum Singleton (best), Static Holder, or DCL + volatile. Eager init if startup cost is acceptable.
// BAD: Not thread-safe static DatabasePool instance; static DatabasePool getInstance() { if (instance == null) // Thread A and B both see null instance = new DatabasePool(); // both create! return instance; } // BEST: Enum enum DatabasePool { INSTANCE; // Thread-safe, serialization-safe, reflection-safe public Connection getConnection() { ... } }

#1–10: OOP Fundamentals
1. Encapsulation — Bundle data + methods; hide internals with private fields
2. Abstraction — Expose what, hide how; interfaces/abstract classes
3. Inheritance — IS-A relationship; subclass extends parent behavior
4. Polymorphism — One interface, many forms; runtime dispatch via overriding
5. Composition — HAS-A; prefer over inheritance for flexibility
6. Law of Demeter — Talk only to direct friends; a.b.c() is a violation
7. Tell Don't Ask — Tell objects what to do; don't query state then act
8. Value Object — Immutable, equality by value (Money, Email, Point)
9. Immutability — final fields, defensive copies; thread-safe by design
10. Cohesion — Class/method does ONE thing well; related things together
SOLID
#11–15: SOLID Principles
11. SRP — One class, one reason to change; UserService ≠ UserEmailer
12. OCP — Open for extension, closed for modification; add via new classes
13. LSP — Subtypes substitutable for supertypes; Square ≠ extends Rectangle
14. ISP — Clients shouldn't depend on methods they don't use; fat → thin interfaces
15. DIP — Depend on abstractions; inject via constructor; enables testing
Creational
#16–20: Creational Patterns
16. Singleton — One instance; Enum is best; use sparingly
17. Factory Method — Let subclass decide which class to create
18. Abstract Factory — Factory of factories; creates families of objects
19. Builder — Step-by-step construction; handles optional params; returns this
20. Prototype — Clone existing objects; implements Cloneable or copy constructor
Structural
#21–27: Structural Patterns
21. Adapter — Convert interface; wraps incompatible class; like power adapter
22. Bridge — Decouple abstraction from impl; vary both independently
23. Composite — Tree of part-whole; leaf + composite share same interface
24. Decorator — Wrap to add features; stacks; same interface as wrapped
25. Facade — Simple interface to complex subsystem; single entry point
26. Flyweight — Share intrinsic state; separate extrinsic; millions of objects
27. Proxy — Surrogate for another object; lazy, caching, protection, remote
Behavioral
#28–38: Behavioral Patterns
28. Observer — Subject notifies observers; 1:N; EventBus, listeners
29. Strategy — Family of algorithms; client swaps at runtime; interface-based
30. Command — Request as object; undo/redo; queue; macro
31. State — Change behavior with state; like a state machine; eliminates conditionals
32. Template Method — Define skeleton; subclasses fill hooks; invariant steps
33. Iterator — Sequential access without exposing structure; hasNext/next
34. Chain of Responsibility — Pass request along handler chain; may stop
35. Mediator — Central hub; objects communicate via hub; reduces coupling
36. Memento — Snapshot state; restore later; originator/caretaker/memento
37. Visitor — Add operation without modifying class; double dispatch
38. Interpreter — Grammar for language; parse and evaluate; AST nodes
GRASP
#39–44: GRASP Principles
39. Information Expert — Assign responsibility to class with the info
40. Creator — B creates A if B contains/records/uses A
41. Low Coupling — Fewer dependencies → easier to change
42. High Cohesion — Related responsibilities together; focused class
43. Controller — First object to receive system event (Facade, Use Case)
44. Polymorphism — Use interfaces/overriding instead of type-checking conditionals
Java
#45–50: Java Specifics
45. equals/hashCode contract — Equal objects must have equal hashCode; same fields in both
46. Comparable vs Comparator — Comparable: natural order (in class); Comparator: custom order (external)
47. PECS — Producer Extends, Consumer Super; <? extends T> to read, <? super T> to write
48. Optional — Represent "maybe absent"; use map/flatMap/orElse; don't use isPresent/get
49. Stream API — filter/map/reduce/collect; lazy until terminal op; avoid side effects in lambdas
50. Thread Safety — volatile (visibility), synchronized (atomicity), Atomic* (single-var), Lock (complex)

📋 Question Bank

OOP & SOLID Questions

Q: What's the difference between Abstraction and Encapsulation?
Abstraction: WHAT an object does — hiding implementation details behind interfaces. "User doesn't need to know how sort() works, just that it sorts." Achieved via abstract classes, interfaces.

Encapsulation: HOW it does it securely — bundling data + methods and restricting direct access via access modifiers (private fields, public getters). Guards against invalid state.

Memory trick: Abstraction = hide complexity. Encapsulation = hide data.
Q: Can you give a real example of LSP violation?
Square extends Rectangle: Rectangle has setWidth/setHeight independently. A Square must keep sides equal, so setWidth(5); setHeight(3) would give area=9 not 15. Any code expecting Rectangle behavior breaks when given a Square.

Fix: Don't make Square extend Rectangle. Use a common Shape interface or make both independent classes. LSP: "All subtypes must be substitutable for their base type without breaking the program."
Q: How do you apply OCP in practice?
Use Strategy pattern or polymorphism to add new behaviors without modifying existing code.

Example: Payment processing. Instead of if/else on payment type, create PaymentStrategy interface with processPay(). Each new payment method (UPI, Crypto) just implements the interface — zero modification to existing code.
Q: When does ISP matter in Java?
When you have fat interfaces forcing classes to implement methods they don't use. E.g., a Worker interface with work() and eat() — a Robot implements Worker but doesn't eat → must provide empty/exception implementation.

Fix: Split into Workable and Feedable interfaces. Classes implement only what they need. This is why Java's Serializable, Runnable, Comparable are tiny single-method interfaces.

Design Pattern Questions

Q: When would you use Builder vs Constructor?
Use Builder when:
• 4+ parameters (telescoping constructor problem)
• Many optional parameters
• Need to create immutable objects step-by-step
• Parameters of same type (easy to mix up)

Pizza pizza = new Pizza.Builder("large").cheese(true).pepperoni(true).build();

Use Constructor when: few required params, no optionals, simple object creation.
Q: Explain Decorator with a real example
Coffee shop: Base coffee + add-ons.
Coffee c = new SugarDecorator(     // +$0.25
              new MilkDecorator(   // +$0.50  
                new SimpleCoffee() // $1.00
              )
            );
c.getCost(); // 1.75
Key insight: Avoids combinatorial subclass explosion. Without Decorator, you'd need classes for CoffeeWithMilk, CoffeeWithSugar, CoffeeWithMilkAndSugar, CoffeeWithSugarAndVanilla... (2^n subclasses for n add-ons!)
Q: Factory Method vs Abstract Factory — when to use which?
Factory Method: One product, subclass decides which concrete type. "Create ONE thing, but let the subclass choose." E.g., Logger factory that creates FileLogger or DBLogger.

Abstract Factory: Family of related products. "Create a SUITE of things that work together." E.g., UI factory that creates matching Button + Checkbox + TextField all in Windows style OR Mac style.

Signal: If you hear "theme", "look-and-feel", "family", "kit" → Abstract Factory.
Q: How does Command pattern enable Undo/Redo?
Each command implements execute() and undo(). Maintain a stack:
Deque<Command> history = new ArrayDeque<>();
// Execute
cmd.execute(); history.push(cmd);
// Undo
Command last = history.pop(); last.undo();
Real world: Text editors (Ctrl+Z), database transactions, macro recording. Commands can also be queued, logged, or replayed for audit trails.
Q: Strategy vs Template Method — which to prefer?
Strategy (composition): Inject algorithm as object. Change at runtime. Test easily with mock strategies. Prefer this — follows Composition over Inheritance.

Template Method (inheritance): Algorithm skeleton in parent, steps in subclasses. Can't change at runtime. Tight coupling. Use when steps truly belong in the hierarchy (like JUnit's test lifecycle).

Rule: If you'd need more than 2 subclasses for variants → Strategy.
Q: Design a thread-safe Singleton in Java
Three good options:
1. Enum (BEST): enum Config { INSTANCE; } — JVM guarantees one instance, serialization-safe, reflection-safe
2. Static Holder: Inner class loaded lazily by JVM class loader — thread-safe without synchronized
3. DCL + volatile: private static volatile DB instance; with double-checked locking

❌ Avoid: synchronized getInstance() (performance), eager without need (may fail early)
Q: When to use Observer vs Event Bus?
Observer: Direct reference between subject and observer. Synchronous. Simple. Good when subject needs to know its observers.

Event Bus (publish-subscribe): Complete decoupling. Publisher doesn't know subscribers. Usually async. Good for large systems, cross-module communication. Spring's ApplicationEventPublisher, Guava EventBus.

Event Bus = Observer pattern + decoupled routing layer.

Case Study Questions

Q: Design Parking Lot — what are the key classes?
Enums: VehicleType {BIKE, CAR, TRUCK}, SlotStatus {AVAILABLE, OCCUPIED}
Entities: Vehicle(licensePlate, type), ParkingSlot(id, type, status), ParkingTicket(id, slot, vehicle, entryTime), ParkingFloor(id, slots[])
Services: ParkingLot (Singleton), ParkingAttendant, FeeCalculator (Strategy for hourly/flat)
Patterns used: Singleton (ParkingLot), Strategy (FeeCalculator), Factory (slot allocation), Observer (display board updates)
Q: Design LRU Cache — which data structures?
HashMap + Doubly Linked List:
• HashMap: O(1) lookup (key → node reference)
• DLL: O(1) move-to-front on access, O(1) remove LRU from tail

class LRUCache {
  int capacity;
  Map<Integer, Node> map = new HashMap<>();
  Node head, tail; // dummy nodes
  // get: find in map, moveToFront, return val
  // put: if full, remove tail.prev; add to front
}
Java shortcut: new LinkedHashMap<>(capacity, 0.75f, true) with removeEldestEntry override.
Q: Design BookMyShow — how do you handle concurrent seat booking?
Problem: Two users booking seat A5 simultaneously → oversell

Solutions:
1. Database-level locking: SELECT FOR UPDATE on seat row → pessimistic lock
2. Optimistic locking: version field in Seat → check version on UPDATE
3. Application-level: synchronized block or ReentrantLock keyed by seatId
4. Temporary lock: Lock seat for 5 min during payment window

Best: DB-level + temporary lock for UX (show seat as "processing" during checkout).
Q: How would you implement Splitwise's debt simplification?
Greedy algorithm: Compute net balance for each person (positive = owed money, negative = owes money).
// Sort: payers (positive) and debtors (negative)
// Greedy: match largest debtor with largest payer
while (!debtors.empty() && !payers.empty()) {
  Person debtor = debtors.peek(); // owes most
  Person payer = payers.peek();   // owed most
  double amount = min(|debtor.balance|, payer.balance);
  transactions.add(new Transaction(debtor, payer, amount));
  // Adjust balances, remove settled parties
}
Minimizes number of transactions. O(n log n).
Q: Design an Elevator system — how do you handle scheduling?
Key classes: Elevator(floor, direction, state), ElevatorController, Request(floor, dir)

SCAN Algorithm (like disk scheduling):
• Elevator moves in one direction serving all requests in that direction
• When no more requests in that direction, reverses
• Similar to how real elevators work

Simple dispatch: Assign request to elevator with minimum |currentFloor - requestFloor| that's going in the same direction or is idle.
