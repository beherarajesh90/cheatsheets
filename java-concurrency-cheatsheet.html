01

Fundamentals

The vocabulary interviewers expect you to use precisely.

Concurrency

Structuring a program as independently-progressing tasks. On a single core, this is interleaving — tasks take turns. It's about dealing with many things at once.

Parallelism

Tasks literally executing at the same instant on separate cores. It's about doing many things at once. Parallelism requires multiple cores; concurrency doesn't.

Process

An independent OS unit with its own address space, heap, and file/socket handles. Expensive to create; isolated by default — crashes don't cross process boundaries.

Thread

A schedulable execution unit inside a process. Shares heap and static memory with sibling threads, but keeps its own stack, program counter, and register set.

Thread lifecycle

Every java.lang.Thread occupies exactly one Thread.State at a time:

StateMeaningHow you get there
NEWCreated, not yet startednew Thread(...) before .start()
RUNNABLEEligible to run — actually running or waiting for CPU time from the OS schedulerafter .start()
BLOCKEDWaiting to acquire a synchronized monitor held by another threadcontending on a monitor lock
WAITINGWaiting indefinitely for another thread's actionObject.wait(), Thread.join(), LockSupport.park()
TIMED_WAITINGWaiting with a timeoutsleep(ms), wait(ms), join(ms), tryLock(t, unit)
TERMINATEDRun completed or exited via exceptionrun() returns
Common trapBLOCKED is specifically about synchronized monitor contention. A thread waiting on a ReentrantLock is WAITING/TIMED_WAITING, not BLOCKED — interviewers use this to check you understand the two lock families are tracked differently by the JVM.

Race conditions & critical sections

A race condition is a correctness bug that appears only when the relative timing of threads changes the outcome. It requires: (1) shared mutable state, (2) at least one writer, (3) no synchronization enforcing an order. A critical section is the code region that touches the shared state and must run with mutual exclusion to remove the race.

Counter.java — classic read-modify-write race
// count++ is NOT atomic: read, add, write — 3 steps.
// Two threads interleaving those steps lose an update.
class Counter {
  private int count = 0;
  void increment() { count++; }   // racy
}

Amdahl's Law — the theoretical speedup ceiling

Every real program has a portion that can't be parallelized (setup, I/O, merging results). Amdahl's Law quantifies how that serial portion caps your maximum possible speedup, no matter how many cores you throw at the parallel portion:

Speedup(N) = 1 / ( (1 - P) + P/N )

P = fraction of the program that IS parallelizable (0 to 1)
N = number of processors/cores

Worked example: a job is 90% parallelizable (P = 0.9) and you throw 8 cores at it (N = 8): Speedup = 1 / (0.1 + 0.9/8) = 1 / (0.1 + 0.1125) = 1 / 0.2125 ≈ 4.7x — not 8x, because that 10% serial slice is paid in full regardless of core count. Push N → ∞ and the speedup still can't exceed 1/(1-P) = 10x — the serial 10% alone becomes the entire bottleneck.

Parallelizable fraction PMax speedup as N → ∞ (1/(1-P))
50%2x
90%10x
95%20x
99%100x
Amdahl vs GustafsonAmdahl's Law assumes a fixed problem size and asks "how much faster does the same job finish?" — pessimistic about adding cores. Gustafson's Law flips the assumption: as you add cores, you typically also scale up the problem size (bigger datasets, more simulation steps) rather than holding it fixed, so measured real-world speedups on big-data/HPC workloads are often far better than Amdahl's Law alone would predict. Interviewers use Amdahl's Law to test whether you understand that adding threads has diminishing, bounded returns — it's the mathematical reason "just add more threads" isn't a universal fix.

ThreadBasics.java

Interrupt is cooperativeinterrupt() only sets a flag and unblocks blocking calls (sleep, wait, join, blocking I/O) by throwing InterruptedException. It never forcibly stops a thread. CPU-bound loops must poll Thread.currentThread().isInterrupted() themselves. Never swallow InterruptedException silently — either rethrow, restore the flag with Thread.currentThread().interrupt(), or handle and exit the loop.

ThreadFactory & naming

Custom ThreadFactory implementations name threads for observability (thread dumps, profilers), set daemon status, priority, and uncaught-exception handlers before threads ever run:

ThreadFactory factory = r -> {
  Thread t = new Thread(r);
  t.setName("worker-" + t.threadId());
  t.setUncaughtExceptionHandler((thread, ex) -> log.error("died", ex));
  return t;
};

Deprecated / dangerous APIs

Thread.stop(), suspend(), and resume() are deprecated/removed — they stop a thread mid-operation, leaving shared objects in a corrupted, half-updated state with no chance to release locks cleanly. Use a shared volatile "running" flag or interruption instead.

ThreadLocal — per-thread state without synchronization

A ThreadLocal<T> gives each thread its own independent copy of a variable — no two threads ever see each other's value, so there's no race to synchronize against. Internally, every Thread carries a small ThreadLocalMap keyed by the ThreadLocal instance itself.

RequestContext.java
private static final ThreadLocal<String> requestId =
    ThreadLocal.withInitial(() -> "none");

requestId.set(UUID.randomUUID().toString());  // visible only on this thread
String id = requestId.get();
requestId.remove();   // MANDATORY when the thread is pooled — see the leak warning below
ThreadLocal<T>InheritableThreadLocal<T>
Visible to child threads spawned inside?No — each thread's copy is independent from birthYes — a child thread inherits a snapshot of the parent's value at the moment it's created
Updates after child creation propagate?N/ANo — it's a one-time copy at thread creation, not a live link
Typical usePer-request context in a thread-per-request server, SimpleDateFormat instance reusePassing a logging/trace context down to worker threads spawned by the request thread
The classic memory-leak gotchaA ThreadPoolExecutor reuses its threads across many tasks. If a task sets a ThreadLocal value and never calls remove(), the value (and everything it references) stays pinned in that pool thread's ThreadLocalMap forever — a slow, hard-to-diagnose memory leak, and in a server, a way for one request's data to leak into a later unrelated request handled by the same pooled thread. Rule: every set() on a pooled thread needs a matching remove() in a finally block. Virtual threads sidestep this in the common case — they're normally used once and discarded rather than pooled — but the discipline still matters if you ever wrap virtual-thread work with pooling. ScopedValue (section 06) removes the footgun entirely by making the unbind automatic.

Java Memory Model (JMM)

The rulebook for when one thread's writes become visible to another. This is the section interviewers use to separate people who've memorized synchronized syntax from people who understand why it's needed.

Modern CPUs and compilers reorder instructions and cache values in registers/store-buffers for performance. Without a memory-model guarantee, thread B might never see thread A's write, or see writes in a different order than A issued them. The JMM defines happens-before: if action X happens-before action Y, X's effects are guaranteed visible to Y.

The happens-before rules

  1. Program order — within a single thread, each action happens-before every later action in that thread's program order.
  2. Monitor lock — an unlock on a monitor happens-before every subsequent lock on that same monitor (by any thread).
  3. Volatile — a write to a volatile field happens-before every subsequent read of that same field.
  4. Thread start — Thread.start() happens-before any action in the started thread.
  5. Thread join — every action in a thread happens-before another thread successfully returns from join() on it.
  6. Transitivity — if X happens-before Y and Y happens-before Z, then X happens-before Z.
  7. Interruption — a call to interrupt() happens-before the interrupted thread detects it (via exception or isInterrupted()).
  8. Final field freeze — a final field's value, once set in the constructor, is guaranteed visible to any thread that gets a reference to the object after construction — provided the reference didn't escape mid-construction.

volatile

volatile guarantees visibility and ordering (no reordering across the volatile access, via a memory fence), but not atomicity for compound operations.

private volatile boolean running = true;   // visibility: good use — a flag, single writer
private volatile int counter = 0;
counter++;   // STILL RACY — read+increment+write isn't atomic even with volatile

Safe publication

An object is safely published when other threads are guaranteed to see it in a fully-constructed, non-corrupt state. Safe ways to publish:

  • Initialize it in a static initializer (JVM guarantees this via class-loading locks).
  • Store the reference in a volatile field, or an AtomicReference.
  • Store it in a final field of a properly constructed object (final field freeze).
  • Guard both the write and every read with the same lock.
  • Hand it off through a thread-safe collection (e.g. a BlockingQueue).

Common visibility bugs

Stale-read infinite loop

A worker loop checks a plain (non-volatile) boolean stop flag set by another thread. The JIT may cache the field in a register and the loop never observes the change — spins forever. Fix: make the flag volatile.

Broken double-checked locking

Lazily initializing a singleton with two null-checks around a lock, but without volatile on the field, lets another thread observe a partially-constructed object due to instruction reordering. Fix: mark the field volatile (this is exactly what makes DCL work post-Java 5).

synchronized vs ReentrantLock

Two ways to get mutual exclusion — one built into the JVM's object header, one a library class built on top of AQS.

How synchronized actually works

Every object has a header containing a mark word that encodes its lock state. The JVM escalates through states to keep the uncontended case nearly free:

StateWhenCost
BiasedOnly one thread has ever locked this objectNear-zero — a CAS once, then just a check
Thin / lightweightA second thread locks it, but never concurrentlyLow — CAS-based spin lock, no OS involvement
Fat / heavyweightReal contention detectedHigher — inflates to an OS-level monitor, blocked threads parked by the OS
JDK noteBiased locking was disabled by default and later removed (JDK 15+, fully gone in JDK 18+) because modern JIT/GC work made the CAS overhead of skipping it negligible, while biased-locking's revocation cost was a real tax on today's multi-threaded, virtual-thread-heavy workloads.

How ReentrantLock works — AQS

ReentrantLock (and most of java.util.concurrent.locks) is built on AbstractQueuedSynchronizer (AQS): a single volatile int state field (0 = unlocked, N = held with N reentrant acquisitions) plus a CLH-variant FIFO wait queue of parked threads, all updated via CAS.

FeaturesynchronizedReentrantLock
AcquisitionImplicit (block/method)Explicit lock() / unlock()

Try without blockingNoYes — tryLock(), tryLock(timeout)
Fairness optionNo (always effectively unfair)Yes — new ReentrantLock(true)
Multiple wait conditionsNo — one implicit condition (wait/notify)Yes — newCondition(), as many as needed
Released automaticallyYes, even on exceptionNo — must unlock() in a finally
ReentrantYesYes

ReentrantLockUsage.java
private final ReentrantLock lock = new ReentrantLock();

void transfer() {
  lock.lock();
  try {
    // critical section
  } finally {
    lock.unlock();   // ALWAYS in finally — a missed unlock hangs every future caller
  }
}
Rule of thumbDefault to synchronized — it's simpler, JIT-optimized, and can't leak a held lock. Reach for ReentrantLock only when you need something it can't do: tryLock, interruptible waits, fairness, or multiple condition queues.

Synchronized wrappers vs concurrent collections vs fail-fast iterators

Collections.synchronizedList/Map/Set(...) wraps a plain collection so every individual method call is synchronized on a single lock — correct, but that one lock serializes all access, and multi-step operations (iterate-then-modify, check-then-act) are still not atomic even though each single call is safe. The java.util.concurrent collections above are a different, better design: built for concurrent access from the ground up (lock striping, CAS, copy-on-write) with genuinely atomic compound methods like putIfAbsent and computeIfAbsent.

ThreadPoolExecutor

new ThreadPoolExecutor(
  corePoolSize,      // threads kept alive even when idle
  maximumPoolSize,   // hard ceiling on pool size
  keepAliveTime, unit, // idle timeout for threads above core size
  workQueue,         // buffers tasks once core threads are all busy
  threadFactory,
  rejectionHandler   // invoked when the queue is full AND pool is at max

Execution order when a task arrives: (1) if fewer than corePoolSize threads exist, start a new one; (2) else if the queue has room, enqueue; (3) else if the pool has room to grow to maximumPoolSize, start a new thread; (4) else, reject.

Shutting down an ExecutorService

MethodEffect
shutdown()Stops accepting new tasks; already-submitted and queued tasks still run to completion. Non-blocking — returns immediately.
shutdownNow()Stops accepting new tasks, does not start queued tasks, and attempts to interrupt all actively running tasks. Returns the list of tasks that never started. "Attempts" — a task ignoring interruption keeps running.

// standard graceful-then-forceful shutdown sequence
executor.shutdown();
if (!executor.awaitTermination(30, TimeUnit.SECONDS)) {
  executor.shutdownNow();            // escalate: interrupt everything still running
  executor.awaitTermination(10, TimeUnit.SECONDS);
}
// or, JDK 19+:
try (var pool = Executors.newFixedThreadPool(4)) {
  pool.submit(task);
}   // close() shuts down and awaits termination automatically

ScheduledExecutorService

Silent-death gotchaIf a scheduled task throws an uncaught exception, that task's future executions are silently cancelled forever — no log, no crash, it just stops running. Always wrap the task body in try/catch and log, rather than letting an exception escape to the scheduler.

Fork/Join & work-stealing

ForkJoinPool implements divide-and-conquer: a task fork()s subtasks and join()s their results. Each worker thread has its own double-ended work queue; a worker pushes/pops its own tasks from one end and, when idle, steals from the other end of a busy worker's queue — this keeps all cores fed with minimal contention. Backs parallelStream() and the common pool (ForkJoinPool.commonPool()).

class SumTask extends RecursiveTask<Long> {
  protected Long compute() {
    if (small enough) return computeDirectly();
    SumTask left = new SumTask(firstHalf);
    SumTask right = new SumTask(secondHalf);
    left.fork();                       // run async
    return right.compute() + left.join(); // compute one side inline, wait for the other
  }
}

Virtual Threads (Project Loom)

JDK 21 finalized virtual threads: cheap, JVM-scheduled threads that make thread-per-request scale again.

A platform thread maps 1:1 to an OS thread — expensive to create (~MB-scale stack), limited to thousands per process. A virtual thread is a lightweight, JVM-managed continuation multiplexed onto a small pool of carrier platform threads. Millions can exist at once because they're cheap (KB-scale stack, grows/shrinks dynamically) and unmounted from their carrier whenever they block.

Mount / unmount

When a virtual thread performs a blocking operation the JDK understands (blocking I/O, Thread.sleep, most java.util.concurrent locks), the JVM unmounts it from its carrier thread — freeing the carrier to run another virtual thread — and remounts it (possibly on a different carrier) once the operation completes.

Pinning — when unmounting can't happen

A virtual thread stays pinned to its carrier (blocking it, defeating the whole point) when it blocks inside:

  • A synchronized block or method (the monitor is tied to the OS thread) — fix: replace with ReentrantLock, which is virtual-thread-aware.
  • A native method or foreign function call.
  • (Historically) certain Object.wait()/legacy JDK internals — most were fixed by JDK 24; check your version.
Migration checklistBefore adopting virtual threads at scale: audit for synchronized blocks around blocking calls (I/O, network) and swap them for ReentrantLock; remove manual thread-pool tuning built around the old platform-thread cost model; watch for ThreadLocal misuse since a virtual thread's ThreadLocal lives for the (short) task, not a reused pool thread.

When to use virtual threads

Good fitPoor fit
High-concurrency I/O-bound workloads (web servers, thread-per-request)CPU-bound number crunching — no benefit over platform threads, use ForkJoinPool/parallel streams instead

Structured concurrency

Structured concurrency (JEP 480 / preview) treats a group of related subtasks as a single unit: they're forked together, and the parent doesn't proceed until all children complete, fail, or are cancelled — eliminating leaked or orphaned subtasks and unifying error handling and cancellation propagation.

try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
  Subtask<User> user = scope.fork(() -> fetchUser());
  Subtask<Order> order = scope.fork(() -> fetchOrder());
  scope.join().throwIfFailed();     // wait for both; propagate first failure
  return render(user.get(), order.get());
}   // scope close cancels any still-running sibling automatically

Scoped Values vs ThreadLocal

ScopedValue (JDK 21+ preview) is an immutable, structured alternative to ThreadLocal for passing context (request IDs, auth principals) down a call stack — bound for the duration of a lambda, then automatically unbound, and cheaply inherited by child virtual threads without the memory-leak risk of a forgotten ThreadLocal.remove().

CompletableFuture & Async

Composable async pipelines without hand-rolled callback chains.

Chaining methods

apply vs composeSame rule as Java's Optional: use thenApply when your function returns a plain value; use thenCompose when it returns another CompletableFuture — this is exactly map vs flatMap.

allOf / anyOf quirks

  • CompletableFuture.allOf(...) returns CompletableFuture<Void> — it does not aggregate results; you must .join() each original future afterward to collect values.
  • anyOf(...) completes as soon as the first future completes (success or exception) and returns Object, requiring a cast.
  • A failed future inside allOf makes the combined future fail too, but the other futures keep running to completion in the background regardless.

async variants — the thread that runs your callback

thenApply runs the callback on whichever thread completes the future (could be the caller's thread, or a pool thread — nondeterministic). thenApplyAsync guarantees the callback runs on ForkJoinPool.commonPool() (or a pool you pass explicitly), decoupling stages from whatever thread happened to finish the prior stage.

CompletableFuture.supplyAsync(() -> fetchUser(), executor)
    .thenApplyAsync(User::getOrders, executor)
    .exceptionally(ex -> Collections.emptyList())
    .thenAccept(orders -> render(orders));
GotchaAlways pass your own Executor to the *Async variants in production code. The default (common ForkJoinPool) is shared JVM-wide — a slow blocking call there can starve unrelated parallel streams and other CompletableFuture chains across your whole application.

Synchronization Primitives

The building blocks every higher-level tool above is made from.

Mutex

Binary — locked or unlocked, exactly one owner. Conceptually simplest form of mutual exclusion. Java's synchronized and non-reentrant use of ReentrantLock are mutexes.

Semaphore

An integer permit counter. acquire() blocks if permits are 0, release() increments. A binary semaphore (1 permit) resembles a mutex but, unlike a mutex, has no ownership — any thread can release it, which enables signaling between threads (see Signaling Pattern).

Condition variable

Lets a thread release a lock and sleep until notified, atomically. Java: Object.wait()/notify()/notifyAll() (tied to a monitor), or Lock.newCondition() for multiple independent wait-sets per lock.

Read-write lock

Any number of readers may hold the lock concurrently, but a writer needs exclusive access. Great when reads vastly outnumber writes. Java: ReentrantReadWriteLock, StampedLock (adds an optimistic-read mode).

wait/notify — always inside a loop, always under the lock
synchronized (lock) {
  while (!conditionMet) {     // while, never if — guards spurious wakeup
    lock.wait();
  }
  // proceed
}
// elsewhere:
synchronized (lock) {
  conditionMet = true;
  lock.notifyAll();            // prefer notifyAll over notify unless you can prove single-waiter safety
}

Barriers & latches

Both make threads wait for each other, but a latch (CountDownLatch) is one-shot and asymmetric — some threads count down, others wait — while a barrier (CyclicBarrier) is symmetric and reusable — every participant both arrives at and is released from the same point, repeatedly.

Concurrency Bugs & Challenges

Every classic failure mode, its cause, and how to detect and fix it — the heart of most concurrency interviews.

BugRoot causeFix / prevention
Deadlock Coffman's 4 conditions all hold: mutual exclusion, hold-and-wait, no preemption, circular wait Break any one condition — most practically, a global lock ordering; or use tryLock with timeout + backoff
Livelock Threads actively respond to each other (e.g. both back off simultaneously) but make no progress Randomized exponential backoff / jitter so retries desynchronize
Starvation A thread perpetually loses the scheduler/lock-fairness race to others Fair locks (new ReentrantLock(true)), avoid thread-priority abuse, bounded queues
Lost wakeup notify() fires before the other thread reaches wait() — the signal is missed forever Always check the condition predicate under the same lock before waiting; use a state flag, not the notify itself, as the source of truth
Spurious wakeup POSIX/JVM allow wait() to return without an actual notify (implementation artifact of how waits are implemented on some platforms) Always re-check the condition in a while loop, never an if
Thread leakage Threads/pools created but never shut down, blocked forever waiting on something that never arrives, or exceptions escaping without cleanup Always shutdown() executors (try-with-resources on AutoCloseable executors in JDK 19+), bound queues, monitor thread counts via JMX
Priority inversion A low-priority thread holds a lock a high-priority thread needs, and medium-priority threads preempt the low-priority one, indefinitely stalling the high-priority thread (Mars Pathfinder, 1997) Priority inheritance (temporarily boost the lock holder), priority ceiling protocol, or just avoid OS thread-priority tuning
Thread-pool starvation deadlock A task running on a bounded pool submits a second task to that same pool and blocks waiting on its result (e.g. future.get()) — if every pool thread ends up in this waiting state, the queued dependent tasks can never start, and nothing ever finishes Never block-and-wait on a task submitted to the same bounded pool you're running in; use separate pools for dependent stages, or size the pool to the maximum call depth (fragile), or restructure with CompletableFuture composition instead of blocking
Deadlock example + fix (lock ordering) 
// DEADLOCK: thread A locks(1)->locks(2), thread B locks(2)->locks(1)
// FIX: always acquire locks in a single global, consistent order
void transfer(Account from, Account to, int amt) {
  Account first  = from.id < to.id ? from : to;
  Account second = from.id < to.id ? to : from;
  synchronized (first) {
    synchronized (second) {
      // move money
    }
  }
}
Lost-wakeup-safe signaling pattern

Three rules prevent lost/spurious wakeup bugs together: (1) always hold the lock when checking and changing the condition; (2) use while, never if, around wait(); (3) prefer notifyAll() unless you can prove exactly one waiter can ever proceed.

Thread-pool starvation deadlock example 
// Pool has 2 threads. Both outer tasks submit an inner task to the SAME pool
// and block on its result — the inner tasks can never get a thread to run on.
ExecutorService pool = Executors.newFixedThreadPool(2);

Runnable outer = () -> {
  Future<String> inner = pool.submit(() -> "inner result");
  try { inner.get(); }               // blocks this pool thread forever
  catch (Exception e) { throw new RuntimeException(e); }
};
pool.submit(outer);
pool.submit(outer);   // both of the pool's 2 threads are now stuck waiting — deadlock

Fix: give the inner tasks a separate pool, or replace the blocking get() with a non-blocking CompletableFuture composition (thenApply/thenCompose) so no thread ever has to sit and wait for a peer task on the same pool.

Locking Strategies

Different ways to scope, acquire, and reason about locks.

Coarse-grained vs fine-grained

A coarse-grained lock protects a large region (e.g. one lock for a whole data structure) — simple and safe, but serializes unrelated operations and caps throughput under contention. A fine-grained lock splits protection into smaller independent locks (e.g. one lock per hash bucket — lock striping, as used inside ConcurrentHashMap) so unrelated operations proceed in parallel. The trade-off is complexity and deadlock risk: more locks mean more orderings to reason about.

Reentrant locking

A lock is reentrant if the thread already holding it can acquire it again without blocking on itself — tracked via a hold count, decremented on each matching unlock. Both synchronized and ReentrantLock are reentrant in Java; this is essential for recursive methods and for a method that calls another synchronized method on the same object.

Try-lock & timed locking

tryLock() (immediate) and tryLock(timeout, unit) (timed) let a thread back off instead of blocking forever — the standard technique for avoiding deadlock when a strict global lock order isn't practical: attempt both locks, and if the second attempt fails, release the first and retry after a randomized delay.

Optimistic vs pessimistic locking

PessimisticOptimistic
AssumptionConflicts are likelyConflicts are rare
MechanismAcquire lock before touching dataRead a version/stamp, compute, then CAS-write only if version unchanged; retry on conflict
Contention costThreads block and waitWasted work on retry, but no blocking
Java examplesynchronized, ReentrantLockAtomicInteger.compareAndSet, DB row-version columns, StampedLock optimistic read
Best whenHigh contention, long critical sectionsLow contention, short operations

Two-phase locking (2PL)

A transaction protocol (mostly discussed in DB/distributed-systems contexts, but a favorite interview curveball in concurrency rounds too): a growing phase acquires locks and never releases any, followed by a shrinking phase that only releases and never acquires. Guarantees serializability, but — despite the name similarity — 2PL does not prevent deadlock on its own; it's typically paired with timeouts or wait-for-graph detection. Variants: Strict 2PL holds all write-locks until commit (avoids cascading aborts); Rigorous 2PL holds all locks (read and write) until commit.

Lock-Free Programming

Coordination without ever blocking a thread — built on hardware-level atomic instructions.

Compare-And-Swap (CAS)

A single atomic CPU instruction: CAS(address, expectedValue, newValue) — writes newValue only if the current value still equals expectedValue, and reports success/failure atomically. Every lock-free Java structure (Atomic*, ConcurrentHashMap, AQS) is ultimately built on this instruction (backed by Unsafe / VarHandle).

AtomicInteger counter = new AtomicInteger(0);
int prev, next;
do {
  prev = counter.get();
  next = prev + 1;
} while (!counter.compareAndSet(prev, next));  // retry loop — the essence of lock-free CAS
// or simply: counter.incrementAndGet();

Categories of atomic operations

CAS is the primitive everything else in this section is built from, but Java's Atomic* classes expose several higher-level shapes on top of it:

CategoryJava methodsShape
Load / Storeget(), set()Read or write the whole value atomically — no torn reads, but no read-modify-write
ExchangegetAndSet(v)Atomically replace the value and return what was there before — the basis of a simple lock (exchange in 1, if you got back 0 you hold it)
Compare-and-swapcompareAndSet(expected, new), compareAndExchange(...)Conditional update — write only if the current value still matches what you last read
Fetch-and-modifygetAndIncrement(), getAndAdd(n), getAndUpdate(fn)Read, apply an operation, write the result — returns the old value
Modify-and-fetchincrementAndGet(), addAndGet(n), updateAndGet(fn)Same, but returns the new value
LongAdder vs AtomicLongUnder high-contention increment-only workloads, AtomicLong.incrementAndGet() makes every thread retry-loop on the same CAS target. LongAdder instead stripes the count across multiple internal cells (one per contending thread, roughly) so different threads usually CAS different cells, then sums them on sum(). Trade-off: faster writes under contention, but reading the total is more expensive and there's no useful compareAndSet — use LongAdder/DoubleAdder for hot counters/metrics, AtomicLong when you need the value itself mid-stream (e.g. as a sequence generator or in CAS logic).

The ABA problem

A CAS sees value A, another thread changes it A → B → A, and the original CAS succeeds thinking nothing changed — even though the underlying object was swapped out and back. Dangerous for lock-free structures built on pointers (e.g. lock-free stacks). Fix: AtomicStampedReference or AtomicMarkableReference, which pair the value with a monotonically increasing stamp/version so a revisited value is still detected as "changed."

Atomic operations & memory ordering

OrderingGuarantee
RelaxedAtomicity only — no ordering guarantee relative to other memory operations
AcquireNo later read/write in program order can be reordered before this one (used on reads/locks)
ReleaseNo earlier read/write can be reordered after this one (used on writes/unlocks)
Acquire-ReleaseBoth — the combination that gives a critical section its boundaries
Sequential consistency (SeqCst)The strongest — all threads agree on a single global order of all SeqCst operations. Java's volatile and default Atomic* ops are effectively this level.
Torn readsOn some platforms, a non-atomic multi-word read (e.g. a 64-bit long/double on a 32-bit JVM) can observe half of an old value and half of a new one — a "torn read." Java's spec exempts plain long/double from atomicity guarantees unless declared volatile, which forces an atomic access.

False sharing

The CPU moves memory between cores in fixed-size cache lines (typically 64 bytes), not individual variables. If two threads write to two different, unrelated variables that happen to sit on the same cache line, each write invalidates the other core's cached copy of the whole line — the two threads end up fighting over cache coherency traffic even though they never touch the same variable. This shows up as mysteriously poor scaling in lock-free counters and per-thread fields packed tightly into one object.

// Two AtomicLongs likely share a 64-byte cache line — every increment
// on one invalidates the other core's cached line, even though the
// counters are logically unrelated.
class Counters {
  AtomicLong reads  = new AtomicLong();   // written by thread A
  AtomicLong writes = new AtomicLong();   // written by thread B — false-shares with reads
}

// Fix: pad, or use @jdk.internal.vm.annotation.Contended (needs -XX:-RestrictContended,
// or java.lang.Class/Thread's own internal use), or simply space hot fields across
// separate cache-line-sized objects/array slots.
Where it actually mattersThis is a senior/staff-level differentiator, not a day-one concept: it explains why LongAdder's internal cells are deliberately padded, and why splitting one contended counter into several padded per-thread counters can outperform a single AtomicLong even though it looks like "more work." Mention it when discussing why LongAdder scales better than AtomicLong, or when a lock-free structure's benchmark doesn't scale the way the algorithm alone would suggest.

Concurrency Design Patterns

Reusable shapes for coordinating threads, each solving one recurring shape of problem.

Signaling pattern

One thread's action must trigger another thread to proceed. A Semaphore(0) is the cleanest signaling tool: the waiter calls acquire() (blocks since there are 0 permits) and the signaler calls release() — unlike a mutex, there's no ownership requirement, so the releasing thread doesn't need to be the one that "acquired" first. Classic use: ping-pong alternation between two threads, or a producer telling a consumer "data's ready."

Thread pool pattern

Pre-create a fixed set of worker threads that pull tasks from a shared queue, avoiding the cost of spinning up a thread per task. Core components: a task queue, a pool of workers, a rejection policy for overload, and a shutdown mechanism. This is exactly what ThreadPoolExecutor implements (see section 05).

Producer-consumer

Producers add items to a bounded buffer; consumers remove them; the buffer decouples their speeds and provides backpressure once full. Java's BlockingQueue implements this directly — put() blocks when full, take() blocks when empty. This is the pattern behind Kafka, RabbitMQ, Go channels, and most job-queue systems.

BlockingQueue<Task> queue = new ArrayBlockingQueue<>(100);
// producer
queue.put(task);       // blocks if full — natural backpressure
// consumer
Task t = queue.take();  // blocks if empty

Reader-writer pattern

Optimizes for read-heavy workloads by letting many readers proceed concurrently while writers get exclusive access. Fairness policy matters: an unfair implementation can starve writers under constant read load. Real systems: database MVCC (readers see a snapshot, never blocked by writers), Java's ReentrantReadWriteLock.

Future / Promise pattern

Represents a value that will exist eventually, letting the caller keep working instead of blocking immediately. Java's Future is the read-side handle (get() blocks until ready); CompletableFuture is both the promise (settable via complete()) and a composable future — see section 07.

Fork-Join pattern

Recursively split ("fork") a problem into independent subproblems, solve them in parallel, then merge ("join") results — see ForkJoinPool in section 05. Best for CPU-bound, recursively-decomposable work (sorting, tree/graph traversal, numeric reductions).

Double-checked locking

Avoids paying a lock's cost on every call to a lazy-init accessor by checking the condition once outside the lock, and again inside it:

private volatile Singleton instance;   // volatile is NOT optional — see section 03

public Singleton getInstance() {
  if (instance == null) {              // 1st check — avoids locking on the common path
    synchronized (Singleton.class) {
      if (instance == null) {          // 2nd check — someone may have won the race
        instance = new Singleton();
      }
    }
  }
  return instance;
}
Simpler alternativeJava's class-loading is itself thread-safe and lazy, so the initialization-on-demand holder idiom (a private static nested class holding the instance) gets the same lazy, thread-safe singleton with zero synchronization code and no volatile subtlety — prefer it unless you specifically need double-checked locking's shape.

Thread Pool Sizing Cheat Math

The formula interviewers expect when you're asked "how many threads should this pool have?"

threads = N_cpu * U_target * (1 + W/C)

N_cpu      = Runtime.getRuntime().availableProcessors()
U_target   = target CPU utilization, e.g. 1.0 for 100%
W          = average wait time per task (I/O, network, blocking)
C          = average compute time per task
WorkloadRule of thumb
CPU-bound (tight loops, hashing, sorting)N_cpu or N_cpu + 1 — more threads just adds context-switch overhead
I/O-bound (DB calls, HTTP, disk)Much larger than N_cpu — use the formula above, or switch to virtual threads and stop sizing a pool at all
MixedSeparate pools per workload type so a slow I/O task can't starve CPU-bound work, or vice versa

Glossary

One-line definitions for rapid-fire recall.

Monitor

The implicit lock + wait-set every Java object carries, used by synchronized and wait/notify.

AQS

AbstractQueuedSynchronizer — the framework underlying ReentrantLock, Semaphore, CountDownLatch.

Memory fence / barrier

A CPU/compiler instruction preventing reordering of memory operations across it.

Contention

Multiple threads competing for the same lock at the same time.

Reentrant

A lock the same thread can re-acquire without deadlocking on itself.

Fairness

Whether waiting threads are served strictly in arrival order (FIFO) or not.

Thread-safe

Behaves correctly regardless of how concurrent calls are interleaved or scheduled.

Non-blocking / lock-free

No thread ever waits on a lock; progress is guaranteed for the system as a whole (though not every individual thread).

False sharing

Unrelated variables on the same CPU cache line cause needless cache-coherency traffic between cores writing to them.

Torn read/write

Observing a multi-word value as part-old, part-new because the write wasn't atomic.

Fail-fast / fail-safe

Fail-fast iterators throw ConcurrentModificationException on structural change during iteration; fail-safe ones (concurrent collections) never do.

Amdahl's Law

The formula capping a program's maximum speedup by the size of its non-parallelizable portion.

Backpressure

A mechanism that slows a fast producer down to match a slower consumer, instead of letting an unbounded buffer grow forever.

Carrier thread

The platform thread a virtual thread is currently mounted on while it runs.
