01

Fundamentals

The vocabulary interviewers expect precisely, not approximately.

Image

A read-only, layered filesystem snapshot plus metadata (entrypoint, env, exposed ports). Built once from a Dockerfile, run many times.

Container

A running instance of an image — the image's layers plus one thin writable layer on top. Ephemeral by default; delete it and the writable layer is gone.

Registry

A store for images (Docker Hub, ECR, GHCR, GCR). docker push/pull move images to and from it, addressed by repo:tag or a content digest.

Layer

One filesystem diff produced by one Dockerfile instruction. Layers are content-addressed and cached — unchanged layers are reused on rebuild.

Container vs virtual machine

ContainerVM
Isolation unitProcess, isolated via kernel namespacesFull OS, isolated via a hypervisor
KernelShared with the hostIts own kernel
StartupMillisecondsSeconds to minutes
OverheadMBs, no duplicated OSGBs, full OS per VM
Boundary strengthWeaker — shared kernel attack surfaceStronger — hardware-level separation

What actually isolates a container

Two Linux kernel primitives, not magic:

  • Namespaces — give a process its own view of a global resource: pid (process tree), net (interfaces, ports), mnt (filesystem mounts), uts (hostname), ipc, user (UID mapping).
  • cgroups (control groups) — limit and account for resources a process group may use: CPU shares/quota, memory ceiling, block I/O, device access.
Interview framingA container is "just a Linux process with namespaces for isolation and cgroups for resource limits." No hypervisor, no separate kernel — that's precisely why it starts fast and why docker run memory limits are enforced by cgroups, which matters a lot once you put a JVM inside one (see §04).

ENTRYPOINT vs CMD

The pairing interviewers use to check you've actually shipped a container, not just copied a tutorial.

Dockerfile
ENTRYPOINT ["java", "-jar", "app.jar"]
CMD ["--server.port=8080"]

docker run myapp runs java -jar app.jar --server.port=8080. docker run myapp --server.port=9090 replaces CMD entirely, giving java -jar app.jar --server.port=9090 — arguments after the image name override CMD, never ENTRYPOINT. Use exec form (JSON array) so the process becomes PID 1 directly and receives SIGTERM; shell form (CMD java -jar app.jar) wraps it in /bin/sh -c, which swallows the signal.

Layer caching trapOrder instructions from least to most frequently changing. Copying source before installing dependencies invalidates the dependency-install layer on every code change:
Dockerfile — wrong order
## invalidates the mvn layer on every source change
COPY . .
RUN mvn dependency:go-offline
Dockerfile — cache-friendly order
## dependency layer only rebuilds when pom.xml changes
COPY pom.xml .
RUN mvn dependency:go-offline
COPY src ./src
RUN mvn package -DskipTests

Multi-Stage Builds for JVM Apps

Ship the runtime, not the toolchain that built it.

A build stage has Maven/Gradle, the JDK, and every source file. None of that belongs in the image that runs in production — it's attack surface and dead weight. Multi-stage builds compile in one stage and copy only the artifact into a slim final stage.

Dockerfile — Spring Boot, multi-stage
## ---- build stage ----
FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /src
COPY pom.xml .
RUN mvn dependency:go-offline
COPY src ./src
RUN mvn package -DskipTests

## ---- runtime stage ----
FROM eclipse-temurin:21-jre-alpine
RUN addgroup -S app && adduser -S app -G app
USER app
WORKDIR /app
COPY --from=build /src/target/*.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]

Only the jre tag ships to production — no compiler, no build cache, no source. The final image is typically 150–200MB instead of 500MB+.

Going further: jlink and distroless

jlink custom runtime

Build a minimal JRE containing only the modules your app uses (java --list-modules + jdeps to find them). Trims tens of MBs off the runtime; worth it for high-density deployments, not usually worth it for one service.

Distroless base

gcr.io/distroless/java21-debian12 ships a JRE with no shell, no package manager, no coreutils. Smaller attack surface than Alpine, but you lose docker exec sh for debugging — trade visibility for hardening.

Interview answer"Multi-stage builds separate the build environment from the runtime environment so the final image only contains what's needed to run the app — smaller image, smaller CVE surface, and the Dockerfile stays the single source of truth for the build instead of relying on a CI script to assemble the artifact separately."
04

JVM in Containers

The gotchas that separate "it runs in Docker" from "it's tuned for Docker."

Container-aware ergonomics

Before JDK 10, the JVM read /proc/meminfo and saw the host's total memory, not the container's cgroup limit — a JVM in a 512MB container would size its default heap off the host's 64GB and get OOM-killed. Since JDK 10 (backported to 8u191+), -XX:+UseContainerSupport is on by default: the JVM reads cgroup limits directly.

FlagEffect
-Xmx512mFixed heap cap in MB — portable across container sizes only if you set it per-environment
-XX:MaxRAMPercentage=75.0Heap sized as a % of the container's memory limit — the recommended default for containers
-XX:InitialRAMPercentageInitial heap as a % of the container limit
-XX:ActiveProcessorCount=NOverrides the CPU count the JVM sees — pin this if cgroup CPU quota detection misbehaves on older kernels
Classic trap: exit code 137Container killed, exit code 137 = 128 + SIGKILL(9). Almost always the kernel OOM killer, triggered because the JVM's total footprint (heap + metaspace + thread stacks + code cache + direct buffers) exceeded the container's memory limit — not just the heap. Sizing -Xmx to 100% of the container limit leaves nothing for the rest and reliably OOM-kills under load. MaxRAMPercentage=75.0 leaves headroom on purpose.

Thread pools sized off the wrong number

Runtime.availableProcessors() reads the cgroup CPU quota (post-JDK 10), not the host's core count — good. But a thread pool sized as availableProcessors() * N inside a container throttled to 0.5 CPU still rounds up to at least 1, and a service that assumes 8 cores because the host has 8 will over-provision threads relative to its actual quota, causing CPU throttling (visible as latency spikes, not errors) rather than an obvious crash.

Interview framing"CPU throttling under cgroups is silent — the container isn't killed, requests just queue longer. If p99 latency degrades under load but CPU% looks moderate, check cpu.stat's nr_throttled before assuming it's a code problem."
05

Containers for AI/ML Workloads

Training and inference containers fight different constraints than a stateless API.

GPU access

A container shares the host kernel but not its drivers by default — GPU access requires the NVIDIA Container Toolkit, which injects the host's driver libraries and device nodes into the container at run time.

shell
# expose all GPUs to the container
docker run --gpus all nvcr.io/nvidia/pytorch:24.01-py3

# expose a specific GPU by index
docker run --gpus '"device=0"' my-training-image
Common trapThe image's CUDA toolkit version and the host's driver version have a compatibility floor — a container built against CUDA 12.4 fails at model load, not at container start, if the host driver predates it. Match the base image's CUDA minor version to what nvidia-smi reports as supported on the host.

Base images by role

RoleTypical baseWhy
Training (GPU)nvcr.io/nvidia/pytorch, tensorflow/tensorflow:*-gpuPre-built CUDA/cuDNN stack matched to the framework version — building this from scratch is a full day lost to version skew
Inference (GPU)nvcr.io/nvidia/tritonserver, custom cuda-runtime slimRuntime-only CUDA libs, no compiler — smaller and faster to schedule
Inference (CPU)python:3.12-slimNo CUDA layer at all when the model runs fine on CPU (small models, batch scoring)
JVM inference (DJL/ONNX Runtime)eclipse-temurin:21-jre-alpineSame container-aware JVM rules from §04 apply — size the heap, watch native memory used by the ONNX/DJL runtime outside the heap

Model weights: bake in, mount, or fetch

Baked into the image

Reproducible, versioned with the code. Bad fit for multi-GB weights — every rebuild re-pushes gigabytes, and registries have layer size limits to respect.

Volume-mounted

Weights live on a host path or network volume, mounted at run time. Image stays small and rebuilds fast; you now own keeping the mounted weights in sync with the code that expects them.

Fetched at startup

Entrypoint script pulls from S3/GCS/a model registry before starting the server. Flexible and image stays tiny, at the cost of slower cold starts and a network dependency at boot.

Init container pattern

A separate lightweight container fetches weights into a shared volume before the main container starts — common in Kubernetes, keeps fetch logic and serving logic decoupled.

.dockerignore matters more here than anywhere else

ML repos accumulate local checkpoints, __pycache__, notebook outputs, and cached datasets — all of which silently balloon the build context and every layer that COPY . touches.

.dockerignore
__pycache__/
*.ipynb_checkpoints
*.pt
*.ckpt
data/
.venv/
.git/

Docker Compose

Multi-container local stacks, declared once.

compose.yaml — Java API + Postgres + model server
services:
  api:
    build: .
    ports: ["8080:8080"]
    environment:
      DB_URL: jdbc:postgresql://db:5432/app
      MODEL_URL: http://model:8000/predict
    depends_on:
      db:
        condition: service_healthy

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_PASSWORD: devpass
    volumes: ["pgdata:/var/lib/postgresql/data"]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s

  model:
    image: my-inference-server:latest
    deploy:
      resources:
        reservations:
          devices:
            - capabilities: [gpu]

volumes:
  pgdata:

Services resolve each other by name over the Compose-created network — the API reaches Postgres at db:5432, no IP addresses, no manual network wiring. depends_on with a condition waits for an actual health check, not just "container started."

Networking

What's reachable from where, by default.

DriverUse case
bridgeDefault for standalone containers on one host; containers on the same user-defined bridge resolve each other by name
hostContainer shares the host's network namespace directly — no port mapping, no isolation, Linux-only
noneNo networking at all — fully isolated, used for pure compute tasks
overlayMulti-host networking for Swarm/orchestrated clusters
Interview trapThe default (unnamed) bridge network does not provide DNS-based service discovery between containers — that only works on a user-defined bridge network (which Compose creates for you automatically). Two containers on the default bridge must resolve each other by IP.
shell
# publish container port 8080 to host port 8080
docker run -p 8080:8080 myapp

# bind only to loopback
docker run -p 127.0.0.1:8080:8080 myapp

Volumes & Persistence

Containers are ephemeral by design — state has to live somewhere else.

TypeManaged byTypical use
Named volumeDockerDatabases, anything you want Docker to own the lifecycle of
Bind mountYou (host path)Local dev — live-mounting source code or model weights from the host
tmpfsDocker, in-memorySecrets or scratch data that must never touch disk
Common trapA bind-mounted directory keeps the host's file ownership/UID inside the container. If the image runs as a non-root USER with a different UID than the host directory owner, writes fail with permission denied — align UIDs explicitly (--user $(id -u):$(id -g) in dev, or a matching UID in the Dockerfile).

Image Size & Security

Smaller and more locked-down are usually the same set of changes.

Base imageRough sizeShell/pkg manager
eclipse-temurin:21-jdk~450MBYes — full JDK, dev only
eclipse-temurin:21-jre-alpine~180MBYes (musl-based, some native libs behave differently)
gcr.io/distroless/java21-debian12~200MBNo shell at all
Custom jlink runtime + scratch~80–120MBNo — smallest, most build effort

Checklist

  • Run as a non-root USER — a container running as root that escapes isolation is root on the host's kernel.
  • Never bake secrets into image layers with ARG/ENV — they persist in the image history even if a later layer deletes them. Use BuildKit's --secret flag or fetch secrets at runtime.
  • Pin base image tags to a digest or minor version, not latest — reproducibility and predictable CVE scanning.
  • Multi-stage builds so build-only tools (compilers, package managers) never reach the runtime image.
  • Scan images in CI (Trivy, Grype, or the registry's built-in scanner) before deploy, not after.
Trap: secrets in ARGBuild-time ARG values persist in the image's layer history, readable long after the layer that used them.
Dockerfile — leaks the secret into image history
ARG API_KEY
RUN curl -H "Authorization: $API_KEY" https://example.com

docker history on the resulting image reveals API_KEY's value — ARG values are recorded per layer even though they're gone from the final filesystem. Use RUN --mount=type=secret instead, which never persists into a layer.

Common Traps

Every one of these has cost someone a debugging afternoon.

Container exits immediately after docker run

A container lives only as long as its PID 1 process. If your entrypoint is a script that finishes (or a server that daemonizes/forks into the background), PID 1 exits and Docker tears the container down — even though "the app looks started." Run the server in the foreground.

"Port is already allocated"

Another container (often a previous run you forgot to remove) already published that host port. docker ps to find it, or just pick a different host port with -p — the container-side port can stay the same.

docker exec fails on a stopped container

exec runs a new process inside an already-running container's namespaces — a stopped container has no running namespaces to join. Start it first, or use docker cp to pull files out of a stopped container without starting it.

Rebuild doesn't pick up a code change

Usually stale layer caching from a COPY instruction ordered before the code that changed (see §02), or the build context excludes the changed path via .dockerignore. docker build --no-cache confirms whether caching is the cause before you go looking elsewhere.

Environment variable set with ENV isn't visible in a later RUN in a different stage

ENV/ARG scope is per build stage in a multi-stage Dockerfile — nothing from stage one crosses into stage two except what an explicit COPY --from= brings across as files.

Alpine image breaks on a native dependency that works on Debian

Alpine uses musl libc, not glibc. Native libraries built against glibc (common in some Python/ML wheels and JNI bindings) can fail to load or behave subtly differently on musl. If a native dependency is misbehaving only in the Alpine image, that's the first thing to check — switch to a -slim (Debian-based) variant if it's not worth patching around.
